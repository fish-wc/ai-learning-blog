# 口述版

关键词：**slug、对称交集、同尺重算、硬前置拦截、证据等级、归因闭合**；

1. **分母口径理解**：在做Agent评测的时候，我们不会直接把全部case当做可用率的计算分母，主要有三点原因，第一，像**流程中断、pipeline报错这类样本属于框架和链路故障，体现的不是Agent本身业务能力**，混入分母会污染质量指标；第二，两次评测run之间**失败样本数量往往不对称，失败样本恢复还会造成指标虚假上涨**；第三，**未评分样本没有打分结果，本身数学上也无法参与比率运算**，所以质量指标分母只选用已评分case，而时延、步数这类性能指标，我们会保留全量case进行统计。

   1. 问题：计算可用率为什么不用全部case
   2. 凝练：1. 流程中断属于框架故障，不属于agent业务能力。2.失败样本不对称，失败样本回复造成指标虚涨。3.没有打分结果，数学上无法计算可用率。
2. **单case完整归因分析**：拿到一条非满分的case，会完整走完标准化分析流程，首先**拉取全部原始证据**，包含**用户query、工具调用轨迹与返回结果、Agent最终回复还有评测器判词**，先做**硬前置拦截，检查是否技能未加载或者流程中断，如果命中框架问题就直接定一级归因，不再继续分析下游业务错误**；之后严格按照优先级做一级归因，优先排除运行环境、框架、case样本数据、评测器本身的问题，再去判断是不是Agent业务层面的问题；确定一级归因后再做二级分类，分类要绑定对应的业务规则slug，不用模糊抽象描述，区分唯一主分类和次要共存分类，接着通过自动校验或者人工checklist核对轨迹和判词，最后输出带原文引用的证据摘要，给出高、中、低三档置信度，证据不足就标记待人工复核，不会强行给出根因结论。

   1. 问题：单case完整归因分析。
   2. 凝练：1. 拉取全部证据，包括原始query，执行轨迹，评测器判词。2.先判是否存在流程中断类问题。3.然后硬前置拦截，判断是否是环境、框架、case本身问题、测评器问题。4.然后判业务层面问题，分类问题，每个case的问题都能对应业务规则slug。5.输出带原文引文的证据摘要，给出三挡置信度，证据不足标记人工复核。
   3. 再次凝练：拉取case信息，分3级评判，数据评判结果。
   4. 补充框架问题：它是调度、路由、技能加载、工具调用、上下文传递、执行流程的底层运行骨架。Agent 想干活，但是框架这个 “工作台、调度器” 出故障了，导致它根本没法正常去执行业务逻辑，不是模型想错了，也不是业务规则错了。
3. **LLM‑judge评测器不稳定问题**：LLM作为打分评测器本身不是客观真理，存在三类不稳定形态，第一类是**裁量漂移**，也就是Agent实际行为没有变化，但打分松紧发生改变，我们可以用**同尺重算、同run内部判罚一致性双检、翻转case审计**来发现；第二类是**版本漂移**，更换评测器版本或者提示词之后，整体数据集分数发生偏移，应对方式是做好评测器版本登记，换版本之后必须对基线做同尺重算，不能直接对比新旧版本原始分数；第三类是**输出退化与幻觉故障**，会出现判词为空、CoT泄漏、判词和真实轨迹互相矛盾的情况，我们依靠**评**测器健康检查、自动校验逻辑、分歧复核队列，逐条比对判词和轨迹来识别这类问题。

   1. 问题：大模型评测不稳定性。
   2. 凝练：1.裁量漂移。同尺重算、同run内部判罚一致性双验、翻转case审计。2.版本漂移。同尺重算。3.输出退化与幻觉。统计检查、自动校验逻辑、人工复核。
4. **跨run对比口径与归因闭合**：做跨run版本对比的时候，会设计三套口径，分别是两侧各自已评分case用于大盘对外展示、两侧同时有效评分的对称交集作为归因的唯一计算分母、全量case用来披露样本损耗情况；会在对称交集口径下拆解三因素归因，分为模型贡献、评测器贡献、pipeline链路贡献以及未决项，各项相加要和整体分数变化保持闭合，允许很小的小数舍入误差，之后再做分母效应桥接，把归因结果换算回大盘展示口径，同时明确区分归因口径和大盘口径，不会直接拿大盘可用率差值当做Agent真实的能力变化。

   1. 工作：跨run对比口径统一
   2. 凝练：1.对称交集归因，在run A和run B都成功运行的case。2.模型贡献、评测器贡献、pipeline链路贡献以及未决项 各项分数变化相加等于总体分数变化。
5. **根因的证据可追溯性**：所有分析出来的根因结论都必须做到可审计可追溯，会区分证据等级，来自工具调用轨迹的T级证据可信度最高，仅有评测器判词没有轨迹佐证的J级证据可信度次之，纯粹的推测O级证据不能写进正式报告；**每一条根因都要能够定位对应的case_id以及明细表格位置**，引用轨迹或者判词的原文片段，**根因描述会采用A侧行为判决到B侧行为判决再到差异根因的固定格式**，拒绝笼统模糊的概括性描述。

   1. 工作：根因证据可追溯性。
   2. 凝练：1.每一条根因都有对应的case_id和明细。2.根因描述采用对比描述，基线run和对比run。
6. **面向研发的可落地报告输出**：撰写评测分析报告要站在研发负责人的视角，保证产出可以直接安排后续修复动作，报告开头用三句话给出核心结论，每一条结论都标注清楚对应的统计口径；每一类问题都给出case清单的入口，对应到Excel明细sheet；每一条优化建议写清楚责任组件、对应负责人、修改方向以及修复后的验证方案；同时写明本次分析的边界，说明哪些问题报告无法解答，哪些case进入人工复核队列，减少后续来回沟通的成本。

   1. 工作：方面研发落地
   2. 凝练：1. 每条结论标注统计口径。2.每一个问题标注case追查入口。

# 03 · 跨 run 对比分析实战工作流（ptr-823 vs ptr-1038 完整复盘）

> 本篇复盘一次真实的完整分析：同一 244-case 评测集的两次 run，可用率掉了 6 个点，要查清楚为什么、哪些 case 导致的、可能是哪个改动引起的。全程产物在 `progress2/`，可复用流程已沉淀为技能 `skills/compare-xiaoaiclaw-eval-runs/`。
> 读本篇重点看**决策点**：每一步为什么这么做、不这么做会出什么事故。

## 0. 任务开工前：先写提示词，再动手

**决策**：第一阶段不碰数据，先写一份《执行提示词》（`progress2/跨run评测对比分析提示词_ptr-823vs-ptr-1038.md`），把口径、步骤、报告要素、Excel 结构、质量红线全部定死，然后再执行。

**为什么**：这类分析的事故大多不是"算不出来"，而是"口径漂了""分类各写各的""报告和 Excel 对不上"。提示词就是分析的"业务规则目录"——先立法再施工。提示词里最值钱的三样东西：

1. **口径锁定**：认定评测器、阈值、分母规则、归因口径唯一化；
2. **数字校验锚点**：动手前先用脚本直算一组关键数字（各口径可用率、转移矩阵、失败构成），后续一切计算必须复现它们；
3. **质量红线**：禁止编造、不确定写未决、加和必须闭合、引文逐字。

**实战教训**：提示词写完后用多个视角做过一轮对抗评审（需求覆盖/事实核查/可执行性/读者价值/产物可行性），抓出 2 个高危缺陷——①让执行者去核对数据里根本不存在的字段（会逼人编造）；②pp 归因的分母没唯一化（归因账加不平）。**提示词也要评审，这是本次最划算的一步。**

## 1. 第 0~2 步：确定性统计（脚本做，不劳烦 LLM）

先跑脚本算出全部确定性数字并落盘逐 case 证据文件（实战当时脚本名 `build_evidence.py`，沉淀进技能时泛化重命名为 `stats_pipeline.py`）：

| 产物 | 内容 |
|---|---|
| metrics.json | 三口径可用率、分数分布、均分、满分/零分率 |
| transition.json | 转移矩阵 + 各方向 case_id 清单 + 变化分层 |
| fail_structure.json | 失败原因分组（toolUse 丢失/DB 死锁/超时）+ 失败 case 对侧桶分布 |
| evaluator_health.json | reasoning 退化、维度分矛盾、CoT 泄漏标记 |
| case_evidence/<id>.md | 244 份逐 case 证据（query/两侧分数/agent_output/判词原文） |

**为什么逐 case 证据文件要先落盘**：后面每个分析单元只读一份小文件，不重复解析 17MB 的大 CSV；证据文件本身就是审计产物；引用"判词原文"时有据可查。

### 1.1 本案的"分母"问题（口径设计的典型样本）

基线 244 例中有 12 例 pipeline 失败（11 例 toolUse 丢失"轨迹以 toolResult 结尾"+ 1 例 DB 死锁），**压根没有评分**。可用率分母如果用全量 244：

- 失败 ≠ 0 分（技能红线），但也不该进分母，否则链路失败率冒充模型可用率；
- 两侧失败数不对称（12 vs 0），"基线失败 case 本次恢复"会被算成模型提升。

所以三口径并报：①各侧已评分（A 232 / B 244）；②对称交集 232（归因用）；③全量 244。**归因口径唯一化**是关键决策：转移矩阵、pp 换算、反事实全在对称交集一把尺上做（1 例 = 0.431pp），三因素贡献之和严格等于 -6.03pp；再用"分母效应"（拆分子效应 + 分母稀释两笔，合计 -0.32pp）桥接回各自分母口径 -6.35pp。**加和能闭合，报告才可信。**

### 1.2 顺手抓到的口径陷阱

外部例行报告头条写"87.5%→78.28%（-9.22pp）"——复算发现是**混合口径**：87.5% 是基线用 `[测试]` 评测器，78.28% 是本次用 `[正式上线]` 评测器，两侧不是一把尺。同尺实际 -6.03pp。**引用外部数字前必须复算口径**，这条直接写进了技能的慢性问题速查。

## 2. 第 3 步：掉分 case 根因分类（核心交付）

**决策**：失败分类用互斥四族 F1（模型行为）/F2（评测器裁量漂移）/F3（评测器故障）/F4（链路），族内细分（F1a 车控污染、F1b 幻觉、F1c 编排欠缺…），并定三条裁决规则：

1. **归类优先级 F3 > F2 > F1**——判决不可信时无法判行为；行为相同仅判决不同归 F2；
2. **判定树解决边界**（F1e 行为层 vs F2b 裁量层）：两侧行为均"未确认"仅判决不同→F2b；B 侧确有新增未确认行为→F1e；证据不足→F2b+未决；
3. **三套分类映射**：F 族 ↔ 三因素（模型/评测器/pipeline）↔ 结论三分（真实回退/评测噪声/链路失败），保证三处数字对得上。

**根因描述固定模板**：`【A 侧行为/判决】→【B 侧行为/判决】→【差异根因】`，必须含具名细节。正例："A 真实打开热水器判 4 分 → B 只调 SystemControlAgent 且幻觉'都弄好了'判 0 分 → 纯车控误路由+虚假声明"；反例（禁止）："车控污染导致掉分"。**读者不用回查原文就能懂并想出对策**，是这条模板存在的全部理由。

### 2.1 多智能体编排实战

65 个 case（24 掉分 + 10 回补 + 19 持续不可用 + 12 失败恢复）逐例分析 + 4 路深度分析 + 4 路复核，一次 workflow 编排 48 个分析单元：

```
前置（主循环）：统计 + 锚点校验 + 证据文件落盘
   ↓
并行 fan-out：
  24 掉分逐例精析（核心，1 case 1 单元）
  10 回补逐例 · 19 持续不可用分批 · 12 失败恢复分批
  深度分析 4 路：同 run 判罚一致性 / 跨 run 反转 / 域污染逐例裁定 / 评测器健康度裁定
   ↓
对抗复核 4 路：分类抽检（证据引文逐字比对）+ 完整性批判
   ↓
聚合（按任务 label 归桶）→ 覆盖校验（65/65 命中）→ 产出
```

**踩坑记录（值得记住）**：聚合时按数组下标取深度分析结果，漏算了分批任务的偏移量，导致深度结果错位、70 行脏数据混入。**修复方式**：workflow 的 journal 里有每个单元的 label，按 label 精确重建聚合。教训：多智能体结果**用 label 寻址，别用下标**。

**复核的收获**：对抗复核抓出 8 处瑕疵（跨侧挪用证据细节、模板标签缺失、S 标签自相矛盾、责任侧硬定等），其中"证据引文逐字比对"一项 16 条引文全部命中——**引文校验是防编造的最后防线**。

## 3. 第 4~6 步：归因、深度分析、摘除

- **三因素归因**：模型侧 -6.47pp / 评测器侧 +0.86pp / pipeline 侧 0 / 未决 -0.43pp，合计 -6.03pp ✓（闭合以精确分数计：-14/232 = -6.0345%；四个显示值相加为 -6.04，属两位小数舍入差，合计行要注明）。注意结论反直觉：**评测器裁量漂移本次净利好对比侧**（未收尾处罚档位从重→从轻，4 例回补）。
- **深度分析的独立价值**：判罚一致性双检找出同 run 内"同行为一重一轻"8 对——这是"判官是否看见"式不稳定的最强证据，比任何推断都硬。
- **摘除方案的两个用途要分开**：
  - *解释掉点*：摘 S1 域污染（32 例）后差距 6.03→2.48pp，补高危裁量簇+评测器故障簇收敛到 1.11pp；
  - *建稳定集*：摘 S1∪S2 全集反而把差距拉大到 4.10pp（S2 里 5/7 在回补方向，摘掉移除了对比侧的运气回补）。
  两个口径结论相反不矛盾——**用途不同，表述分开**。
- **处置与摘除分开**：评测器故障 case = 重评不摘除；pipeline 失败 = 修重试不摘除；存量缺陷（持续不可用 14 例高危未确认）= 能力优化，不进摘除集。

## 4. 产物工程（报告 + Excel + 校验）

- **报告**：3 句话结论（带口径名）→ 失败类型总表摘要 → §0 边界 → §1 指标（含分母说明）→ §2 归因（转移矩阵/分类/三因素+桥接+校验行）→ §3 深度 → §4 摘除 → §5 总表完整版（合计校验行+净额桥接行）→ §6 优化建议（带编号供回指）→ §7 产物清单；
- **Excel 8 sheet**：字段说明（图例即读）/ 汇总统计 / 四个方向明细 / 全量对照 / 摘除候选；重点 sheet 10 字段含根因描述；query 用**原文**不用摘要（用户反馈项）；
- **追溯闭环**：报告引用 case_id 标 Excel sheet 名 + 全部引用过"全量对照命中"校验清单（28 个引用 28 命中）；
- **数字一致性**：报告与 Excel 来自同一份计算结果（同一 JSON），加 12 项一致性抽查。

## 5. 交付：飞书

- 文档用整篇 markdown 发布（不删改），表格用 sheet_ops 分块重建 8 个工作表（36 块写入、长文本逐字）；
- **教训**：pipeline 参考文档里的飞书目录 token 属于另一套 CLI 鉴权体系，MCP 应用无权限——落到云盘根目录（历史产物同处）并明确告知偏差；机械搬运交给子代理（228KB 数据不过主上下文），主循环只做落位核验；
- 发布后回贴关联产物链接（报告↔表格互链），读者动线闭环。

## 6. 追加：改动归因（提供"变化预览"时的第 8 步）

目标：把失败类型归因到具体改动。本案的分析结构：

1. **候选集**：例行报告"变化预览"的 14 笔 commit + SP 全跨度 diff；⚠️ 清单只覆盖单日，10-08~10-19 中间合入未列入——分析中实际发现清单外提交（`83e5770473` cross-device 路由铁律），**候选集闭合性必须标注**；
2. **失败簇 × 改动透镜**：每个失败簇独立归因，给机制链（改动→机制→失败签名→case 证据）+ 反证 + 置信度；
3. **关键发现——执行通道事实优先于叙事**：外部报告点名 car-automation 两笔改动，但掉分主力 11 例里 10 例的执行通道是 SystemControlAgent（system-control skill），B 侧回复与该 skill 的话术模板逐词吻合——近端嫌疑应转向唯一直接改 system-control 的提交。**"同窗"≠"因果"，要看机制是否接壤**；
4. **评测器换版是独立"改动"**：判罚锚点对换的文本证据（"未收尾→D1≤2"条款消失）足以坐实 8 例判决翻转属尺子效应，验证手段是**交叉重评**而非代码 revert；
5. **反证式结论也有价值**："持续不可用 14 例与改动无关（两侧同罚）"和"12 例失败恢复早于窗口 17 天不可能致因"同样是产出；
6. **验证计划可排期**：`验证编号/改动 hash/目标 case 集/预期行为/判据/方式/前置依赖`，二分顺序（先 system-control 后 car-automation），未决项给"决出条件+取证途径"。

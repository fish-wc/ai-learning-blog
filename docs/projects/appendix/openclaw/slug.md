
# slug（这份评测材料语境下）

**slug = 业务规则的稳定唯一短标识（规则ID）**

示例文档里的例子：`R‑highrisk‑confirm‑only‑yes‑no`、`R‑scene‑closure‑all‑high‑confidence`。

## 通俗解释

1. 业务文档（`iot‑control‑rules.md`）写了一条条业务约束：

> “高危设备控制，只允许反问确认是否执行”
> 给这条规则分配一个**机器可读、名字固定不变的短代号**，这个代号就是 **slug**。

2. 特点：

- 小写、连字符分隔，不使用中文；
- **一旦分配尽量不改**，哪怕规则的中文描述改了，slug保持不变；
- 用来做**跨文档绑定**：二级错误分类 ↔ 业务规则。

> 比如错误分类`HighRiskDirectControl`（高危未确认直接执行），它的锚定slug就是`R‑highrisk‑confirm‑only‑yes‑no`。
> 含义：出现这个badcase，违反的就是slug对应的那一条业务规则。

## 为什么这套评测体系非要用slug？

> 文档原话：**每个问题分类都锚定到业务规则的slug，分类不能拍脑袋起名**。

1. 如果只用中文描述：中文会改、会润色，脚本、统计、历史case就全部对不上；
2. slug是**不变的索引键**：
   - 业务规则库：`slug → 规则原文`
   - 错误分类表：`错误分类ID → 对应哪些slug`
   - badcase证据：记录命中了哪个slug
3. 作用：做自动化校验、统计、回归测试。脚本可以直接读取slug，不需要解析中文自然语言。

## 举个对照

| 项目                     | 内容                                    |
| ------------------------ | --------------------------------------- |
| 业务规则中文             | 高危反问只问是否执行                    |
| **slug（稳定ID）** | `R‑highrisk‑confirm‑only‑yes‑no` |
| 对应的二级错误分类       | `HighRiskDirectControl`               |

## 现实工作里的约束（来自文档）

> 新建二级错误分类，必须写明：**锚定规则slug + trajectory信号 + 典型表现**。
> 没有可以锚定的slug，说明这个分类是拍脑袋想出来的，不允许进入正式分类体系。

### 对比通用IT领域的slug

普通Web开发里slug一般是URL路径别名（例如`how‑to‑use‑agent`）；
**本材料里，slug专指业务规则的唯一短ID，不是网址。**

**一句话结论**：槽位（slot）是"意图—槽位"框架里与意图配套的概念——**意图决定"用户想做什么"，槽位决定"对哪个对象做、怎么做、做到什么值"**。槽位本质就是把自然语言里的关键信息抽成机器可执行的结构化字段（字段名 + 字段值）。

举个例子，"把卧室空调调到 26 度"：意图 = 设备调温；槽位 = 设备=卧室空调、动作=设置温度、数值=26℃。槽位不填满，指令就无法执行。

具体到 houyi 这几个 domain，"槽位"的口径各不相同，这正是你强调"别搞混"的原因：

- **smartMiotNew（意图槽位理解）**：最经典的槽位。对用户 query 做意图分类 + 槽位填充，输出"意图 + 一组槽位"（设备、房间、动作、参数值、时间等），可能还是嵌套槽位树。
- **MiotScene（自动化 action 槽位提取）**：智能场景"如果…就…"里后半段"执行动作"的参数化字段——目标设备、操作类型、参数值（亮度/温度/色温）。它管 action 侧，和 smartMiotNew 管意图/触发侧是两套。
- **MiotQueryRewrite / IotFutureQueryRewrite（query 改写）**：改写本身输出的是文本，但槽位依然关键，因为**改写必须保证槽位保真**——多轮省略（"把灯调亮"→"再亮一点"）时不能把设备/动作槽位改丢改错；很多系统联合输出"改写文本 + 槽位"，或用槽位保留率当评估指标。
- **smartMiotLlmCls（自动化场景分流）**：本质是分类/分流任务，不直接产槽位，它决定 query 该走哪条槽位理解或提取链路。

**IoT = Internet of Things（物联网）**，指智能硬件设备联网互通的技术领域。

**Miot 里的 "M" 基本可以确定是小米的 "Mi"**——即 **Mi + IoT = 小米 IoT**。证据很直接：小米官方的开发者平台域名就是 `iot.mi.com`，全称"小米 IoT 开发者平台"，平台文档里也明确写着"IoT(Internet of Things)"，主要服务米家智能家居、智能家电、可穿戴、智能出行等设备，并且提供"小爱语控和智能联动"能力 。

"Mi" 是小米产品线常用的品牌前缀（如米家 App 的 Mi Home、小米手环 Mi Band），所以 Miot 就是小米生态的物联网体系。结合你前面列的 houyi 各 domain（MiotQueryRewrite、MiotScene、smartMiotNew 等），这些就是小米 IoT 语音助手侧的 NLP 任务。相比之下，**IotFutureQueryRewrite 没有 M 前缀**，说明它走的是另一条独立的 IoT 域（非小米 Miot 主链路），这也对应你之前强调的"别搞混"——两个改写域虽然任务类型一样，但分属不同业务域。



数据已完整读完。先给结论：**一条标准 eval 用例 = 「标识 + 元信息」壳层 + 「Query + Context Info」模型输入 + 「Extra Info」评分参考**，白盒类型下判分完全由 Extra Info 里的 `expected_result` 决定。下面按成分拆解本条数据。

## 一、五个核心成分（本条逐项对应）

**① 用例标识（case_id）**
`1_a51efb248e58419ab8f3d9ce2a58ce87_s2_t1`

- `1_`：批次/来源前缀；`a51efb...`：用例唯一哈希；`s2`：样本/场景序号；`t1`：第 1 轮（单轮所以只有一个 t；多轮会扩展 t2、t3 并携带历史）。
- 这个 ID 同时就是 `request_id`，贯穿全链路，是追溯/对齐的锚点。

**② 元信息（Meta）**：`iot_car`（业务场景）· `hard`（难度）· `单轮`（轮次）· `白盒`（类型）

- 难度和轮次决定统计口径（hard 单独分层、多轮单独评测）；类型决定判分方式——**白盒有黄金标签可离线自动判分，黑盒只有 Query 需要人工/LLM 打分**。

**③ Query（用户输入）**："要出门一天，帮我照看下家里"

- 注意它没有任何显式设备名/动作，属于意图开放的表达，必须靠场景推断才能落设备 → 这正是 `hard` 的来源。

**④ Context Info（环境快照 = 模型实际拿到的上下文）**

- `iot_agent_mock_context.miot_eval_id` 带 `mock_` 前缀：证明是 **eval 专用模拟环境**，不是真实用户数据（隐私隔离）。
- `miot_eval_devices`：20 台设备。每条含 `did / type(urn:miot-spec-v2 品类) / name(用户自定义名) / model / hid+rid(家-房间关联) / real_did / mac / online / properties`。
- `miot_eval_rooms`：3 组家庭拓扑——`家`、`车`、`home{书房/卧室/厕所/厨房/客厅}`，设备靠 hid/rid 挂到房间。
- `miot_extra_param.need_split_device_flag="1"`：同品类多设备时是否拆分的消歧标志。
- **关键设计**：设备清单 = 正样本（门锁、喂食器）+ 大量干扰项（电视、摄像头、路由器、电蚊香、车顶灯…），用来考模型在噪音下筛选品类；设备名还是真实用户风格（"無罪的REDMI 智能电视"、"Fairy Home"），考自定义命名理解。

**⑤ Extra Info（评分参考，不进模型）**

- `expected_result.scenes = ["出行回家-短长期外出"]`：期望命中的业务场景（一级场景"出行回家"下的子场景）。
- `high_confidence = ["门锁","宠物喂食器"]`：该场景下应高置信选中的**设备品类**（注意是品类不是具体设备）；`low_confidence = []`。
- `reasoning`：标准答案的推理链，同时是 LLM-as-judge 的评分参考。
- `topology_result`：期望的设备拓扑解析结果（home→room→category→device），即要下发给执行链路的**结构化输出**。
- `annotation_should_confirm = false`：无需人工复核；`domain = "iotCopilot"`：本条归属的评测域。

**为什么答案是门锁 + 宠物喂食器**："出门一天"命中"出行回家-短长期外出"子场景，该子场景的高置信可操作品类集 = {门锁, 宠物喂食器}——门锁管离家安防（防忘锁/确认锁好），喂食器管宠物定时照看。扫地机、摄像头等虽然"在家"，但不在该场景高置信集合里，就是干扰验证项。

## 二、最容易忽略/最需要抓住的点

1. **输入隔离**：模型只拿到 `Query + Context Info`；`Extra Info` 是判分基准，绝不能混入模型输入（白盒评测的第一红线）。
2. **评分以品类为单位**（`门锁`而非"小米智能门锁 2"）：评测的是"场景理解 + 场景→品类映射"，避免过拟合具体设备名，也允许设备清单变化。
3. **Context 是"带干扰项的环境快照"**：难度不在 Query 长不长，而在"意图模糊 + 噪音设备 + 多家庭拓扑（车/家）+ 自定义设备名"的组合筛选。
4. **topology_result 与 expected_result 是两套输出**：前者是结构化的设备-房间落地（给下游），后者是场景/品类语义答案（给判分），别混为一谈。
5. **元信息四件套 + domain 决定一切统计口径**：改任何一项（如把白盒当黑盒评）都会污染整个评测结论。

## 第 0 步：最裸的版本（50 行脚本）

假设我们什么都不懂，就想要一个"收到消息→调模型→回复"的机器人：

```js
// toy-bot.js —— 我们的第一版
const ws = require("ws");
const { Anthropic } = require("@anthropic-ai/sdk");

wss.on("connection", (socket) => {
  socket.on("message", async (data) => {
    const reply = await anthropic.messages.create({
      model: "claude-opus-4-6",
      messages: [{ role: "user", content: data.toString() }],
    });
    socket.send(reply.content[0].text);
  });
});
```

50 行，能跑，是不是挺好？**是的 —— 只要你只有一个用户、只发一条消息、
模型永远不挂、网络永远不抖。**

现在开始逐个引入真实世界。每引入一个，我们的脚本就会死一次，
然后长出一站。

## 问题 1：模型挂了怎么办？—— 长出「attempt 层」

**场景**：模型服务返回 500，或者你的 API key 限额了。

玩具脚本的表现：`await` 抛异常 → 进程没接住 → **整个机器人崩了**。
所有正在聊天的用户一起死。

**真实事故有多疼？** 我们仓库 10 月 13 日有个提交（`9d139e9a63`）就是干这个的：
设备问"天气"没有回复。排查发现模型在反复调同一个工具（死循环），
熔断器把整个 run 掐了，但掐得太狠 —— 模型一个字都没来得及说，设备端收到空回复。
**"防护"本身成了事故**，这就是这层问题的微妙之处。

所以需要一层"尝试"的概念（**attempt**，`run/attempt.ts:1273`）：
（两层 lane 在 `run.ts:152` 进入 —— 见问题 2）

- 一次尝试 = 从调模型到拿到回复的完整过程
- 失败了？换个鉴权凭据（auth profile 轮换）再试
- 还失败？换备用模型（fallbacks 列表）再试
- 全失败？返回错误，**但只影响这一条消息，进程还活着**

> **attempt 层存在的意义**：把"失败"从"事故"降级为"日常"。
> 模型挂是常态不是异常，这层的全部工作就是让常态不伤人。
> 这也是术语表里"Model failover 两级机制"（profile 轮换 → 模型 fallbacks）的家。

## 问题 2：用户连发 3 条消息怎么办？—— 长出「队列层」

**场景**：用户手速快，1 秒内发了 3 条："帮我查天气" "北京的" "顺便明天也查"。

玩具脚本的表现：3 个 `await` 并发跑。后果取决于运气：

- 好的情况：3 条回复乱序到达，用户看到"明天晴"出现在"北京"前面
- **坏的情况：3 个并发进程同时读写同一个会话文件**（后面问题 4 会讲这文件），
  文件交错写入 → 历史记录损坏 → 之后每一轮对话都是坏的

这不是理论风险。我们的实测（10-29，见前篇第 9 站）：三条消息同秒到达，
系统日志打出 `lane wait exceeded: waitedMs=7439 queueAhead=1` ——
第二条在队列里等了 7.4 秒，但**会话文件从头到尾只有一个人在写**。

所以需要队列决策层（`queue/settings.ts:32`）+ 两层 lane（`run.ts:152` 起）：

- **session lane**（每会话一个，并发=1）：同一会话的 run 互斥排队
  —— 解决"写坏会话文件"
- **global lane**（进程级，默认并发 4）：全进程总闸 —— 解决"20 个会话同时
  打模型，把配额打爆、把账号打限流"

**collect 模式的意义**就露出来了：排队不是傻等 —— 积压的消息会在下一轮
**合并成一个 prompt**（"用户连说了三件事"一次说给模型），省 token 也省一轮调用。

> **队列层存在的意义**：把"并发"变成"受控的串行"。
> 代价是延迟（第二条等 7 秒），换来的是正确性（文件不坏）和配额安全。
> 这是所有消息系统最经典的取舍：**宁可慢，不能错**。

## 问题 3：消息从哪来？往哪回？—— 长出「路由层（sessionKey）」

**场景**：现在接了 Telegram、飞书、Discord 三个渠道，500 个用户。

用户 A 在 Telegram 问"我上次问的问题"，玩具脚本 `messages: [{...}]` 每次
都是空的 —— **它根本没有记忆**。要记忆就得有"会话"，要会话就得回答：
"这条消息属于哪个会话？"

- Telegram 用户 123 的消息 → 会话甲
- 飞书群里用户 456 的消息 → 会话乙
- 同一个飞书用户私聊 → 会话丙（和群里不是一个会话！）

这个"属于哪个会话"的答案就是 **sessionKey**。它的格式是设计出来的答案：

```
agent:{agentId}:{channel}:{groupId}:u-{userId}
  │        │         │         │         │
  哪个助手  哪个渠道   哪个群    （私聊无）  哪个用户 ← 多租户隔离键
```

**为什么格式长这样？** 因为它精确回答了隔离的四个维度：不同助手分开、
跨渠道分开、群聊私聊分开、**不同用户必须分开**（最后这个是 SaaS 多租户的命根子，
`u-{userId}` 错了就是数据越权 —— 实验 6 那个"跨用户 cwd 错位"bug 之所以定级严重，
就是因为它让用户 B 的会话文件里装着用户 A 的上下文）。

CLI/TUI 为什么是 `agent:dev:main` 三段？因为本地直连没有渠道/群/用户三要素，
全空，只剩两段 —— 这是**退化情形**，就像身份证号不填国籍字段时留空。

> **路由层存在的意义**：给每条消息一个稳定的"户口地址"。
> 没有它：无记忆（不知道跟谁聊）、无隔离（张三看到李四的对话）、
> 无队列目标（问题 2 的 session lane 按 key 分道，没有 key 就没有分道）。

顺带注意：**路由层是全渠道共用的**。代码里 telegram/discord/slack/飞书……
所有渠道的消息最终都汇入同一个 `dispatchInboundMessage`（`auto-reply/dispatch.ts`）→
同一条 reply 管线。渠道只负责"收发"（适配各家 API），进到管线里就是统一格式。
这就是为什么改一次队列逻辑，所有渠道同时受益。

## 问题 4：记忆存在哪？怎么不被写坏？—— 长出「session 文件层」

**场景**：有了会话，历史消息要落盘。用什么存？

玩具脚本的想法：一个 JSON 大文件，每次收到新消息读出来、append、写回去。

**死于三处**：

1. **并发写**：问题 2 的排队解决了"同一会话内"，但进程内还有别的写者
   （后台压缩任务也要改历史）—— 需要锁
2. **崩溃一致性**：写一半断电，整个 JSON 解析失败 → **全部历史报废**。
   所以用 JSONL（一行一条，append-only）：崩了最多丢最后一行，前面的完好
3. **越写越大**：聊了 500 轮，每次都把 50 万 token 塞给模型 → 又贵又超窗口。
   所以有 **compaction**（长对话摘要压缩）—— 这也解释了为什么 transcript
   必须是 `parentId` 链表：压缩后从摘要节点岔出新链，旧链保留可追溯
   （还记得实验 1 红线吗：绕过 `SessionManager.appendMessage` 裸写会切断链条）
4. **多租户规模**：5000 个用户的会话文件放本地磁盘行不通 → 二开把存储后端
   换成 Redis（权威）+ JFS（文件）双写 —— 实验 6 排查的"三源 sessionId 对不齐"
   就是这层的真实事故：reset 用了 UUID、transcript 用了 hex，三处 ID 不一致

> **session 文件层存在的意义**：让记忆**可持久、可恢复、可压缩、可扩展**。
> 它是整条链路的"状态底座" —— 前面的路由层决定写到哪个文件，
> 后面的编排层决定什么时候读、什么时候压缩。

## 问题 5：模型要用工具怎么办？—— 长出「工具循环层」

**场景**：用户问"现在几点"，模型说"我需要执行 `date` 命令"。

玩具脚本：`messages.create()` 一次就完了，没有"执行工具"这回事，回复不了。

真实做法是**循环**（pi-agent-core 的 `runLoop`）：

```
把问题给模型 ←──────────────────┐
  ↓                              │
模型回复（可能带 toolCall）          │
  ↓ 有 toolCall                   │
执行工具，结果追加进上下文 ──────────┘
  ↓ 没有 toolCall（纯文本）
结束，这就是最终回复
```

**循环为什么需要防护？** —— 想象模型抽风了：调 `date` → 看到结果 →
又调 `date` → 又看到结果 → …… 无限循环 = 无限烧钱。这不是笑话，
`tool-loop-detection.ts` 里四种探测器对应四种真实的抽风姿势：

| 探测器                     | 抓什么                    | 阈值                           |
| -------------------------- | ------------------------- | ------------------------------ |
| `generic_repeat`         | 重复调用哈希相同的调用    | 10 次 warning / 20 次 critical |
| `ping_pong`              | A 和 B 两个工具互相踢皮球 | 同上                           |
| `known_poll_no_progress` | 轮询型工具但结果从不变化  | 同上                           |
| `global_circuit_breaker` | 总量兜底                  | 30 次熔断                      |

而且开头那个真实事故的教训也在代码注释里：critical 命中后**不是立刻杀**，
先 block 几次并"回灌"提示让模型自救（`CIRCUIT_BREAKER_ABORT_AFTER_BLOCKS = 3`），
给模型留出说话的机会 —— 否则用户端就是空回复。

> **工具循环层存在的意义**：让模型从"会说"进化到"会做"，同时**给"会做"装刹车**。
> 没有刹车：一次死循环烧掉一天的预算，且用户永远等不到回复。

## 问题 6：500 个用户同时问，一台机器扛不住怎么办？—— 长出「网关层」

**场景**：单进程跑不动了，要横向扩容、要管理连接、要安全。

这引出了链路最前面的几站：

- **网关 + 校验/幂等**（站②）：5000 个客户端连着你。网络会重试 ——
  同一条消息发两遍，玩具脚本会跑两遍模型（双倍花钱）。幂等去重
  （`agent:${idempotencyKey}`）让重试无害。参数校验挡住畸形请求，
  不让它深入系统浪费资源。**这是守门员的站**。
- **编排层**（`runReplyAgent`，站⑤）：回复一条消息远不止"调模型"——
  要发打字中提示（用户体验）、先跑压缩预检（上下文太长就先摘要）、
  跑记忆 flush（该记的先记）、准备流式分段投递（长回复拆块）……
  这些事必须有个人统筹。**这是管家的站**：自己不干活，安排别人干活。

> **这两站存在的意义**：守门员挡掉不该进来的（省资源），
> 管家安排好进来之后的每一步（不出乱子）。它们和业务逻辑零耦合 ——
> 所以 33 个渠道、N 个 agent 共用同一条管线而不互相干扰。

## 全景回顾：把 8 站按"挡什么灾"重新排一遍

```
                    一条消息的旅程（按防御的灾难排序）

  用户/渠道                    ┌─ 站② 校验+幂等 ──────── 挡：重试风暴、畸形请求
     │                        ├─ 站③ 路由(sessionKey) ── 挡：记忆混乱、数据越权
     ▼                        ├─ 站④ 队列决策 ────────── 挡：并发写坏会话、配额打爆
  ┌──────────┐   站① 入口     ├─ 站⑤ 编排 ──────────── 挡：流程缺环（忘压缩/忘提示）
  │ 网关     │───────────────►├─ 站⑥ 两层 lane ──────── 挡：资源失控（同会话互斥+总量闸）
  └──────────┘                ├─ 站⑦ attempt ────────── 挡：模型故障扩散（隔离+重试）
     ▲                        ├─ 站⑧ 工具循环 ───────── 挡：死循环烧钱（+熔断刹车）
     │                        └─ 站⑨ 投递+落盘 ──────── 挡：崩溃丢数据（JSONL+parentId链）
  回复/落盘
```

**一张表总结每站的"存在理由"**（面试级答案）：

| 站                     | 存在意义（一句话）               | 如果删掉会发生什么                |
| ---------------------- | -------------------------------- | --------------------------------- |
| ① 入口（客户端/渠道） | 统一消息的进出格式               | 每个渠道各造一套轮子，永远对不齐  |
| ② 校验+幂等           | 让重试无害、让垃圾止步           | 重试=双倍计费；畸形请求穿透到核心 |
| ③ 路由 sessionKey     | 给消息上户口（隔离与记忆的前提） | 无记忆；跨用户数据泄漏            |
| ④ 队列决策            | 定义"忙时新消息"的语义           | 连发消息行为不可预期              |
| ⑤ 编排                | 统筹回复前的所有准备             | 压缩/记忆/提示各唱各的，时序错乱  |
| ⑥ 两层 lane           | 受控并发（会话内串行+总量封顶）  | 文件写坏；配额打爆；全服限流      |
| ⑦ attempt             | 隔离与消化失败（故障转移粒度）   | 一次模型抖动=全服崩溃             |
| ⑧ 工具循环+熔断       | 让模型会做事且有刹车             | 功能残缺；或死循环烧钱            |
| ⑨ 投递+落盘           | 崩溃安全的持久化与回包           | 断电全丢；回复乱序                |

## 为什么是"分层"而不是"一个大函数"？

到这里可以回答标题的问题了。把上面所有防护写进**一个 3000 行的函数**行不行？
功能上"行"，但：

1. **改不动**：改队列逻辑会碰到模型重试代码，改重试会碰到落盘 ——
   牵一发动全身，没人敢碰
2. **测不了**：没法单独测"幂等去重"，必须把整个函数跑起来
3. **复用不了**：新接一个渠道（比如钉钉），理论上要复制整个大函数改一遍

分层之后：每站只对自己的问题负责（**单一职责**），站与站之间只传
明确的参数（`followupRun` 这个打包对象）—— 于是：

- 实验 4 我们 30 行就写了个插件挂在工具循环上（`before_tool_call`），
  一行链路代码没碰
- 二开把 session 存储从文件换成 Redis（实验 6），只动"落盘"那一站，
  上面的队列路由编排全部原样复用
- 33 个渠道共用同一条管线，改一处全受益

**这就是架构分层的本质：不是把代码切短，而是把"变化"关进各自的笼子。**
渠道经常变 → 关在渠道适配层；模型经常换 → 关在 attempt/failover 层；
存储经常演进 → 关在 session 层。各自变化，互不传染。

## 自查：这次的问题不一样

不再问"每站做什么"，改问"为什么需要它"：

1. 删掉 attempt 层，第一个崩溃的场景是什么？（模型 500 → 异常上抛 → 进程死）
2. collect 模式省了什么？多付了什么代价？（省：合并 token、少一轮调用；付：延迟）
3. 为什么 sessionKey 必须包含 `u-{userId}`？（多租户隔离 —— 少了就是越权）
4. 熔断器为什么"先 block 三次再杀"而不是立即杀？（留机会让模型自救输出，
   否则用户收到空回复 —— 真实事故教训）
5. transcript 为什么是 parentId 链不是普通列表？（支持压缩/分支时的历史重构）
6. 所有渠道共用一条 reply 管线，好处是什么？（改一处全受益 —— 排队/幂等/熔断全渠道共享）
7. "分层"的本质收益用一句话说？（把变化关进各自的笼子，互不传染）

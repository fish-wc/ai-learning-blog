# 01 · 评测分析领域与企业工作流程

## 1. 这个领域在做什么

被测对象是一个 **Agent（智能体）系统**——用户用自然语言下达任务（"到家后帮我布置看电视的环境"），Agent 自主规划、调用工具（查设备拓扑、控制家电、查状态）、生成回复。评测分析回答三个递进的问题：

1. **跑得怎么样**（单 run 质量剖析）：完成度多少、问题集中在哪；
2. **为什么掉/涨了**（跨 run 对比归因）：这次比上次差了 N 个点，是模型变了、评测尺子变了、还是链路抖了；
3. **怎么修**（可执行的优化建议）：每类问题对应谁来改、改什么、怎么验证。

## 2. 核心概念速查

| 概念 | 含义 | 关键注意 |
|---|---|---|
| **run / batch** | 一次评测执行（如 ptr-823、ptr-1038），带环境版本号 | 比较两次 run 前先确认数据集、模型、配置是否可比 |
| **评测集（dataset）** | 一批固定 case（如 iot场景评测集 244 条），跨 run 复用 | case_id 稳定才有跨 run 对齐的基础 |
| **case** | 一条评测样本：query + 期望 + 运行记录 + 评分 | 每个 case 的完整证据是归因的最小单元 |
| **评测器 / 打分器（evaluator）** | 给 case 打分的模型或规则（LLM-as-judge 为主） | 多评测器并存时必须锁定"认定评测器"，否则口径混算 |
| **判词（judge reasoning）** | 评测器给分的文字依据 | 是证据但不是事实——LLM judge 会漏看、会漂移、会退化 |
| **可用率 / 满足率 / 完成度** | 可用率=分数≥阈值的占比；满足率=满分占比；完成度=均分 | 每个指标必须带分子/分母和口径名 |
| **门禁（gate）** | 硬性通过线（如"大盘可用率跌幅 ≤1pp"） | 门禁判定只认指定口径，观测指标另列 |
| **打分尺度差** | 不同评测器对同一批输出打分宽严不同 | 跨 run 换了评测器必须"同尺重算"再比 |
| **口径A / 口径B** | 全量 domain 加权 vs 有效 case 交集对齐 | 两口径互为交叉验证，差异要有解释 |

## 3. 企业内部的例行评测闭环

以下流程提炼自企业真实的例行评测报告（20261020 / 20261021 两份报告结构）：

```
每日构建（分支 ptr-YYYY-MM-DD，run 标识 ptr-NNN）
   └→ 例行评测跑 14 个评测集（全域）
        └→ 自动生成例行评测报告
             ├─ 一、整体结论：门禁判定（三口径交叉验证：口径A 域级加权 / 口径B 有效 case 交集 / 逐 case 可用净）
             ├─ 二、变化预览：代码提交清单 + system prompt diff（变化定位 Top N）
             ├─ 三、分 domain 指标：逐 case Diff 汇总、打分器稳定性判定、
             │      真实变差机制/责任组件、组件级归因（第四层）
             ├─ 四、效率指标：步数/token/时延（含口径更正声明）
             ├─ 五、归因分析：错误子类型分布 + 与基线变化（步骤级归因体系）
             ├─ 六、关键结论 / 七、建议下一步动作
             └─ 发布飞书文档，评论区 @责任人认领排查（20261020 报告评论区有实例）
```

### 3.1 报告里体现的几个行业级实践

1. **三口径交叉验证**：域级加权、case 级交集、逐 case 净变化三个口径同向才算结论稳健；门禁只认其一。
2. **基线打分器口径固化**：老基线用旧打分器、新 run 用新打分器时，先"换尺重算基线"再对比（例：iot 场景集基线换 `[测试]IOT_意向性` 后 58.82%→87.50%），并明文声明尺度差。
3. **打分器稳定性判定**：对每个"变差 case"用 LLM 逐 case 比对两侧轨迹，判"打分器不稳定 vs 真实变差"，从变差集合里剔除尺子噪声后才算真实回归。
4. **三层归因 + 组件归因矩阵**：第 1 层·上下文面（skills/SP 规则冲突）→ 第 2 层·改动面（同窗 commit 嫌疑）→ 第 3 层·模型（机制分布），再落一张"域·机制→责任组件→诱因→已排除"矩阵（责任组件含 tools 运行时一层）；改动面只写"嫌疑/同窗"，无变更记录可对齐时不写成根因。
5. **责任组件 + Owner 制**：每类问题标注责任组件（真实报告的取值：模型 / tools 运行时 / skills / 对话历史 / SP），对应到人（skill owner、评测组、后端），报告文档评论区 @ 到人认领。
6. **效率指标独立观测**：步数、token、时延与质量分开看；发现口径问题当期更正并写"口径更正"声明（如 query 前 token 剔 0 值）。

### 3.2 作为分析者你在闭环中的位置

你的产出有三类读者：

| 读者 | 想看什么 | 你要给什么 |
|---|---|---|
| mentor / 测试负责人 | 结论可信吗？门禁过不过？ | 口径声明 + 交叉验证 + 边界（本报告无法回答什么） |
| 研发负责人 | 我的模块有问题吗？先修哪个？ | 责任侧归因 + 具体 case + 可排期的验证/修复建议 |
| 下一个分析者（包括未来的你） | 数字怎么算的？结论怎么来的？ | 可审计中间产物 + 可复跑脚本 + 校验清单 |

## 4. 分析者的日常决策框架

遇到任何分析问题，按这个顺序想：

1. **可比性**：两次 run 的数据集/模型/评测器/环境一致吗？不一致先声明边界；
2. **口径**：这个数字的分子分母是什么？失败 case 怎么处理？两侧是不是一把尺？
3. **证据**：我的结论有哪级证据？换个说法——如果被问"你怎么知道"，答案是轨迹原文还是猜测？
4. **归因优先级**：环境/框架/数据/评测器的问题不能算到 Agent 头上（详见 02 篇的一级归因优先级）；
5. **可执行性**：读我报告的人明天能做什么？给不出动作的结论要重写。

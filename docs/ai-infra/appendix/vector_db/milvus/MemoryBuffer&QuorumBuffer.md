# MemoryBuffer & QuorumBuffer（Woodpecker 两大缓冲区）
> 背景：Woodpecker 是**零磁盘架构**，日志最终要写到远端对象存储。对象存储网络RTT高，如果每条写入都直接调用一次对象存储接口，延迟会爆炸。所以**引入缓冲区做批量攒写**，MemoryBuffer 和 QuorumBuffer 就是两种不同的缓冲模式，对应 Woodpecker 的两种部署形态。

**MemoryBuffer** ：Woodpecker内嵌模式使用的内存缓冲区。写入数据先暂存在单机内存，攒批后一次性上传对象存储。只有数据成功写入对象存储，才返回写入确认。若节点宕机，内存中尚未刷入对象存储的数据会丢失。

**QuorumBuffer** ：Woodpecker独立服务模式的仲裁内存缓冲区。基于Raft协议，数据同步至多节点内存副本；当多数（quorum）节点内存写入成功，即向客户端返回写入成功，后台异步持久化到对象存储。单节点故障不会丢失已确认写入的数据，写入延迟更低，需要多节点集群支撑。

## 1. MemoryBuffer（内存缓冲区，**内嵌模式 Embedded 默认**）
### 工作原理
1. StreamingNode收到DML写入请求，数据先放进**本机内存MemoryBuffer**
2. 攒一批数据 / 达到定时阈值（默认200ms），一次性批量上传到对象存储
3. 批量成功写入对象存储之后，才向客户端返回「写入成功」
4. 数据全程**不会落地本地磁盘**，完全在内存攒批

### 特点
优点：实现简单，资源开销小，适合中小集群
缺点：**单点风险**。**单机内存攒批，攒够了一次性推到对象存储；宕机丢未刷盘的数据。**
- 如果这个StreamingNode进程宕机，内存里还没刷到对象存储的数据会直接丢失
- 没有多副本，只能依靠对象存储最终持久化，一致性偏弱

## 2. QuorumBuffer（仲裁缓冲区，**独立服务模式 Service 使用**）
> 为了解决MemoryBuffer宕机丢数据的问题，引入内存多副本，基于Raft仲裁。
### 工作原理
1. 写入请求到达Woodpecker集群，数据写入**多个节点的内存缓冲区**
2. 当超过半数（quorum，仲裁）节点在内存成功写入副本，就立刻返回客户端「写入成功」
3. 后台再异步批量把日志持久化到对象存储

> 重点：**确认成功只需要内存多数派副本落内存，不等对象存储写入完成**，降低写入延迟；后续后台慢慢刷对象存储。

### 特点
优点：
1. 高可用：单个节点宕机，其他节点内存里还有副本，数据不丢
2. 写入延迟更低，不需要等待对象存储IO完成才返回客户端
 缺点：
1. 需要部署多节点Woodpecker集群，资源开销更大
2. 实现复杂，要维护Raft组做副本同步

## 两者对比
| 特性 | MemoryBuffer | QuorumBuffer |
| ---- | ---- | ---- |
| 使用场景 | Woodpecker内嵌模式 | Woodpecker独立服务模式 |
| 副本 | 单机内存，无副本 | 多节点内存Raft多数派副本 |
| 确认写入成功时机 | 等待批量数据写入对象存储完成 | 多数节点内存写完就返回，异步刷对象存储 |
| 宕机风险 | 未刷到对象存储的数据丢失 | 只要quorum副本写入内存，单节点宕机不丢数据 |
| 性能 | 较高延迟，资源省 | 低延迟，资源开销更大 |

## 联想学习
- MemoryBuffer：适合小规模部署，简单，**牺牲一点可用性换简单**
- QuorumBuffer：生产大集群高吞吐场景，**内存多副本保证高可用，降低写入RTT**
两者都属于**零磁盘架构**：缓冲区只在内存，**都不使用本地磁盘持久化日志**。


## 面试高频追问
Q：QuorumBuffer 既然内存就确认成功，那对象存储还需要写吗？
A：需要。内存副本是临时的，一旦整个Woodpecker集群全部宕机，内存数据会消失，最终持久化仍然依赖对象存储。内存quorum保证单节点故障不丢；对象存储保证集群级持久化。

Q：MemoryBuffer 为什么会丢数据？不是零磁盘吗？
A：零磁盘指**不用本地磁盘永久存日志**，不是内存永不丢失。内存是易失的，断电/进程崩溃内存数据直接清空，还没上传对象存储的数据就丢了。

# Raft 一致性协议
概述：Raft是分布式一致性算法，用于保证集群多节点数据一致，可容忍少量节点故障。拆分为三大核心机制：Leader选举、日志复制、安全性。集群节点有三种状态：Leader、Follower、Candidate。依靠任期(Term)和多数派(Quorum)仲裁机制：写请求需要复制到半数以上节点确认，才算提交成功。

## 1. 三种节点角色
1. **Leader（领导者）**：集群唯一接收写请求的节点，负责把日志复制给所有Follower，周期性发送心跳保活。
2. **Follower（跟随者）**：被动角色，不主动发起请求；只响应Leader、Candidate的RPC请求；收到Leader心跳就确认Leader存活。
3. **Candidate（候选人）**：临时角色。Follower长时间收不到Leader心跳，就变成Candidate，任期+1，发起投票竞选Leader。

> **Term（任期）**：逻辑上的时间片段，单调递增，类似“朝代年号”。每一轮选举就是一个新Term；任何消息携带旧Term都会被直接拒绝，用来防止旧Leader干扰集群。

## 2. Leader选举流程（3节点集群A/B/C）
1. 初始状态：3个节点都是Follower。
2. 节点A长时间没有收到Leader心跳 → 变成Candidate，Term从1变成2，给自己投一票，然后向B、C发送投票请求。
3. B、C收到投票请求，发现Term更新，并且本轮还没有投过票，就投A。
4. A拿到**超过半数（Quorum，仲裁）选票**（3节点，≥2票），成功当选Leader。
5. A周期性发送心跳包给B、C，维持Leader身份；B、C收到心跳，就保持Follower。
6. 如果Leader A宕机，B/C收不到心跳，超时后重新发起新一轮选举。

> 关键点：**Quorum（多数派）**，就是我们前面Woodpecker QuorumBuffer里的Quorum来源。3节点集群只要2个节点确认，就代表多数派；集群最多容忍1个节点故障。5节点集群需要3个确认，可以容忍2个节点宕机。

## 3. 日志复制（核心，和Woodpecker强相关）
客户端写请求发给Leader：
1. Leader收到请求，生成一条日志，写入自己本地日志。
2. Leader并行把这条日志复制给所有Follower节点。
3. 当**超过半数节点（多数派）成功写入这条日志**，日志标记为**已提交（committed）**。
4. Leader通知所有Follower：这条日志已经提交，大家把日志应用到状态机。
5. Leader返回客户端：写入成功。

重点：**只要多数节点写成功，就认为写入成功，不需要等待全部节点**。少数慢节点后续会自动追赶补齐日志。

## 4. 安全性保证
Raft有严格规则：**一旦某条日志被提交，这条日志永远不会被修改、覆盖，保证所有节点最终一定执行相同的日志序列**。就算Leader宕机，新选出的Leader一定包含所有已提交日志。

## 5. 和Milvus Woodpecker的关联（重点！）
Woodpecker独立模式的 **QuorumBuffer 就是基于Raft的多数派机制**：写入一条日志，同步到多个Woodpecker节点内存；只要**超过半数节点内存成功写入日志，就返回客户端写入成功**，后台再异步持久化到对象存储。
> 这就是为什么QuorumBuffer单节点宕机不会丢已经确认写入的数据：多数节点内存已经保存这条日志。

etcd 底层本身就是完整Raft实现，用来做元数据存储、选主。

## 6. 优缺点
优点：逻辑清晰，相比Paxos更容易理解、工程落地，etcd是最经典落地案例。
缺点：所有写请求必须经过Leader节点，Leader会成为单点瓶颈。

# FAISS数据库不足

核心根源：**FAISS 只是一个向量检索库（C++/Python 算法库），不是完整的向量数据库**。**内存里的向量 ANN 近似最近邻检索**；数据库的配套能力（持久化、分布式、事务、权限、元数据过滤）全部都没有内置，需要业务代码自己封装实现。

## 1. 持久化：索引默认在内存中，需要自己写逻辑做 save/load，没有内建的数据落盘与恢复机制
- FAISS 的索引对象运行时全部放在内存。进程一旦崩溃、重启，内存里的索引直接消失。
- 虽然有 `faiss.write_index()` / `faiss.read_index()` 可以把索引序列化写入磁盘，但这**只是一次性导出文件**，不是数据库那种实时持久化。
- 没有自动定期落盘、崩溃自动恢复、增量快照。要自己写代码：定时保存、管理索引文件、备份。
> 举个例子：程序突然宕机，还没调用 write_index，新加入的向量全部丢失。

## 2. 动态更新：大多数高性能索引(如 IVF、HNSW)对"增量插入"和"删除"支持有限，频繁增删会导致索引退化，需要定期全量重建

### IVF（倒排索引）
IVF 在使用前需要**训练聚类中心**。训练完成后，聚类中心点就固定不变了。
- 可以调用 `add()` 追加向量，但是新增向量如果分布和训练样本差异大，聚类桶会失衡，**召回率会悄悄下降（索引退化）**；
- FAISS**没有真正的物理删除**。所谓删除只是打一个 tombstone（标记失效），向量还在索引里，检索后业务代码过滤掉已删除ID；
- 大量新增/删除之后，唯一恢复召回率的办法：**全量向量重新训练 + 重建索引**。

### HNSW（图索引）
HNSW**不需要预训练，可以持续增量插入**，这点比 IVF 友好。
但是删除依然是标记删除；如果**频繁大量删除**，向量图会断裂、碎片化，召回率持续下跌，也需要定期重建索引来整理图结构。

一句话总结：**FAISS 的增删都不是传统数据库那种轻量实时更新，频繁变更会慢慢降低检索质量，而且不会报错，属于静默退化**。


补充概念：

自动定期落盘
**落盘 = 把内存里的数据写到磁盘（硬盘）保存**
- 自动定期落盘：数据库后台**自动定时**把内存中新写入的数据持久化到磁盘，不需要手动调用保存函数。
- 比如 MySQL：你插入一条数据，先写内存缓冲区，后台线程每隔一段时间自动刷到磁盘。就算进程意外崩溃，最多丢失一小段最近的数据。
- FAISS 只有手动调用 `faiss.write_index(index, "index.bin")`，才会把整个索引一次性写入磁盘。不会后台自动保存，如果不手动执行，进程一挂，内存里新加的向量全部消失。

增量快照
**快照：某一时刻索引的完整备份文件**
- 全量快照：每次备份，把**全部向量**重新导出一份完整文件。FAISS 的 `write_index` 就是全量快照。向量库1000万条，每次保存都要读写全部1000万条向量，很慢，文件巨大。
- **增量快照**：只保存**从上一次快照之后新增/修改**的数据，而不是全量导出。节省IO、时间、存储空间。
> 举例子：上次快照有1000万向量，之后新增了1万条。增量快照只保存这新增1万条，而不是重新导出全部1000万。

FAISS 原生**不支持增量快照**。每次保存索引，都必须序列化整个索引，属于全量导出。


场景：我们用FAISS上线一个向量检索服务，持续插入用户Embedding向量
1. 服务启动，加载历史索引文件 `index.bin` 到内存。
2. 用户不断上传文本，服务调用 `index.add(new_vector)`，向量只存在内存。
3. 此时服务器突然断电 / 程序崩溃：
    - 所有 `add` 进去但**没有手动执行 write_index** 的向量全部丢失。磁盘上还是旧的 `index.bin`。
4. 如果我们想做保存，只能定时写代码：每隔半小时，执行一次 `faiss.write_index(index, "index.bin")`
    - 这是**全量写入**，向量越多，耗时越长；
    - 在写入的这几十秒，服务不能修改索引，否则文件损坏；
    - 不存在“只保存半小时内新增向量”的增量快照。



## 3. 分布式扩展：原生不支持水平扩展，数据量超过单机内存上限就很难处理 
- FAISS 原生是**单进程库**，没有内置分布式集群、分片、节点通信。
- 它有 `IndexShards`，但这只是**同一台机器内多GPU/多CPU分片**，不是跨机器分布式。
- 如果向量总量超过单机内存，你需要自己手动做数据分片：把向量切成多份放到不同机器，查询时请求所有分片，拿到结果后自己做归并取TopK。这整套逻辑都要自己开发，没有开箱即用。

## 4. 服务化能力：没有内建的多租户、鉴权、多副本高可用、标量字段过滤等"数据库该有的东西" 
- FAISS 没有 HTTP/gRPC 服务接口，不是一个可以远程访问的服务，只能嵌入你的程序进程内调用；
- 多租户、账号鉴权、权限控制：完全没有，租户隔离要自己做多份独立索引；
- 多副本、故障转移、高可用：需要自己搭建；
- 标量过滤（例如：检索向量同时过滤 `status=published`、`time>xxx`）：FAISS 索引**只存向量+ID，不存业务元数据**。
> 常规做法：向量ID关联外部MySQL，向量召回后，再去数据库查元数据并过滤。

## 5. 一致性/事务：没有一致性级别的概念，并发读写时的可见性由使用者自己保证 
FAISS 没有事务、没有 MVCC、没有读写隔离级别。
- 多线程并发 add / search，**并发安全要自己加锁控制**；
- 没有“提交”“回滚”的概念；写入一个向量之后，对其他并发查询什么时候可见，完全由你代码控制；
- 没有ACID，无法保证原子性。

# 一句话总结 FAISS 的定位
优点：**单机向量检索性能极强，CPU/GPU加速，ANN算法丰富，高度可定制**，适合PoC、离线实验、静态知识库。
局限：**只是算法库，不是数据库**。持久化、分布式、事务、权限、动态CRUD、高可用全部需要上层业务代码自己封装。

> 对比：Milvus、Qdrant、Pinecone 这类向量数据库，底层很多也是用HNSW/IVF这类ANN算法（甚至内部封装FAISS），但是配备有数据库能力。

# 选型
- 静态数据集，单机，RAG原型/实验：直接FAISS，简单高效。
- 生产环境，向量频繁增删，数据量大，需要高可用、多租户：不要裸用FAISS，选择成熟向量数据库。

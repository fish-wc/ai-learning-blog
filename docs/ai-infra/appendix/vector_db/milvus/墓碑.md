# 删除墓碑 Tombstone

概述：**墓碑就是逻辑删除标记。删除向量时，不会直接抹掉对象存储里原始向量，而是单独记录一条「这个主键已经被删」的标记，这个标记就叫 Tombstone（墓碑），Milvus里存放在Delta Log增量删除日志里**。查询阶段过滤掉标记数据；Compaction阶段永久清理。


## 完整流程例子
场景：集合image_vec，主键1001这条向量，我们执行delete删除
1. **收到删除请求，写入WAL**
SDK发送delete，走Proxy → StreamingNode → Woodpecker WAL，记录删除事件。
2. **生成墓碑（Tombstone），写入Delta Log**
DataNode消费WAL，**不会去对象存储删掉原来1001的向量文件**；而是新增一条Delta Log（删除日志），记录：`主键1001，已删除`，这个记录就是墓碑。Delta Log和Segment数据一起存到对象存储。
> 原始向量还安静躺在Segment文件里，只是多了一条墓碑记录。
3. **QueryNode加载Segment时，同时加载Delta Log（墓碑列表）**
检索的时候，QueryNode内存里：向量索引 + 墓碑清单。
    - ANN索引检索拿到候选向量ID列表
    - **后置过滤**：遍历候选ID，如果ID在墓碑清单内，直接剔除，不返回给用户。
> 用户看起来这条向量被删掉了；但原始向量文件物理上还在。
1. **Compaction阶段：真正清理墓碑，物理删除**
后台Compaction任务启动，读取Segment原始数据 + Delta Log里所有墓碑。
合并Segment的时候，**直接抛弃所有带有墓碑标记的数据**，只把有效向量写入新Segment，新Segment不再带这些墓碑。
新Segment上传对象存储；旧Segment文件后续GC垃圾回收删除，释放存储空间。

## 关键要点
1. **Tombstone = 逻辑删除标记，不是直接删原始向量**
2. 查询时：索引照常检索，**最后根据墓碑过滤掉已删向量**。代价：会多检索到无效候选，增加查询开销。墓碑越多，检索性能下降越明显。
3. 只有Compaction执行完成后，被墓碑标记的数据**才会真正物理清除**。Compaction之前，向量文件一直占用存储。
4. Update/Upsert本质：给旧主键打上墓碑，再插入一条新向量。

## 联想学习
- Flush：Growing Segment → Sealed Segment，写入对象存储
- Tombstone：删除操作生成，记录在Delta Log，实现软删除
- Compaction：合并Segment，**清除墓碑对应的无效向量**，物理回收空间

### 常见问答
Q：为什么向量库不能原地删掉向量？
A: Milvus的索引（HNSW图索引）是复杂图结构，如果删除一条向量就去修改索引，代价极高，会严重拖慢写入。所以采用**逻辑删除 + 后台物理清理**方案。


Q：大量删除，大量墓碑，会有什么影响？
A：检索召回时会扫到很多已经删除的向量，需要过滤，查询延迟上升，存储占用也不会立刻下降，需要compaction清理。

Q：墓碑存在哪里？
A：保存在Delta Log（增量删除日志），和Segment一起存放在对象存储，QueryNode加载Segment的时候同步加载Delta Log到内存。

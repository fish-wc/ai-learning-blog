# 从企业文档到可追溯问答：一次 RAG 链路优化实践

简述： **如何把企业内部大量结构复杂、格式不统一的文档，转化为可以被稳定检索、被大模型理解，并且能够追溯答案来源的知识。**

![完整的智能体工作流](/docs/interview/appendix/resume/整体思维导图.png)

整条链路可以简化为：

```text
企业文档
   ↓
文档解析
   ↓
结构化切片
   ↓
向量化与索引
   ↓
候选召回
   ↓
重排序
   ↓
上下文补全
   ↓
LLM 生成回答
   ↓
Agent / 业务应用
```

真正影响最终效果的，往往不是最后一次 LLM 调用，而是前面每一个环节是否可靠。

---

## 1. 为什么企业文档不能直接丢给大模型？

最开始的问题看起来很简单：

> 用户问一个问题，从公司的文档中找到答案，再交给大模型生成回复。

这就是典型的 Retrieval-Augmented Generation，也就是 RAG。

但真正落地以后，很快会发现三个问题。

### 1.1 文档本身并不“干净”

企业知识库里的文件通常不是统一格式。

可能同时存在：

* PDF
* Word
* Excel
* 制度文件
* 操作手册
* 数据资产材料
* 各种历史版本文档

即使都是 PDF，内部结构也可能完全不同。

例如：

```text
第三章 数据质量要求

3.1 完整性
......

3.2 一致性
......
```

经过解析以后，有时可能变成：

```text
第三章 数据质量要求
......
页码 17
......
3.2 一致性
......
```

一旦文档解析阶段破坏了原始结构，后面的 Embedding 和大模型能力再强，也无法恢复已经丢失的信息。

所以 RAG 的第一步，并不是“选择什么大模型”，而是：

> **先把原始文档转化成相对稳定、可检索的数据结构。**

---

## 2. 第一个核心问题：Chunk 应该怎么切？

文档解析完成以后，需要把长文档切成较小的文本块，也就是 Chunk。

最简单的方法是固定长度切分，例如：

```text
每 500 个字符切一个 Chunk
```

或者：

```text
每 512 Token 切一个 Chunk
```

这种方法实现简单，但在企业文档中很容易出现语义割裂。

例如原始内容是：

```text
5.1 数据完整性评价

完整性主要用于衡量数据字段是否缺失。

计算方式为：

完整字段数量 / 应有字段数量
```

如果刚好在中间被切开：

```text
Chunk A：

5.1 数据完整性评价
完整性主要用于衡量数据字段是否缺失。
```

```text
Chunk B：

计算方式为：
完整字段数量 / 应有字段数量
```

那么用户问：

> 数据完整性怎么计算？

向量检索可能会命中 Chunk B。

但 Chunk B 自己并没有说明：

> 这个公式计算的是“数据完整性”。

也就是说：

> **检索到了正确文本，但上下文不完整。**

这是一类非常典型的 RAG Badcase。

---

# 3. 从固定切片到分级切片

简述：**用于检索的文本应该足够小，保证语义集中；用于生成的上下文应该足够完整，保证模型理解。**

针对这个问题，我参与优化了文档切片策略。

核心思路并不是单纯增加 Chunk 长度，而是尽可能保留文档原有的层级关系。

例如：

```text
Document
│
├── Chapter
│   │
│   ├── Section
│   │   │
│   │   ├── Paragraph
│   │   └── Paragraph
│   │
│   └── Section
│
└── Chapter
```

实际构建 Chunk 时，会尽量保留：

```text
文档标题
章节标题
小节标题
正文
```

于是原本只有：

```text
计算方式为：
完整字段数量 / 应有字段数量
```

的文本，在进入检索系统时可以带上一部分结构信息：

```text
第三章 数据质量要求

5.1 数据完整性评价

计算方式为：
完整字段数量 / 应有字段数量
```

这样做的目的并不是让 Chunk 变得无限大。

恰恰相反：

> **用于检索的文本应该足够小，保证语义集中；用于生成的上下文应该足够完整，保证模型理解。**

这是我在这段项目中逐渐形成的一个比较重要的认识。

---

# 4. 上下文补全：检索单元不一定等于生成单元

简述：**小块负责“找得准”，大一点的上下文负责“看得懂”。**

即使采用分级切片，也仍然存在一个问题。

小 Chunk 通常更容易精准召回，但携带的信息有限。

因此在检索命中某个 Chunk 后，可以进一步补充它的上下文。

例如命中：

```text
Chunk 27

完整字段数量 / 应有字段数量
```

系统可以根据它保存的结构信息，进一步找到：

```text
Parent Title:
5.1 数据完整性评价
```

必要时再补充：

```text
Previous Chunk
Current Chunk
Next Chunk
```

最后真正送给 LLM 的上下文可能变成：

```text
5.1 数据完整性评价

完整性主要用于衡量数据字段是否缺失。

完整字段数量 / 应有字段数量。
```

因此整条链路变成：

```text
小粒度 Chunk
      ↓
向量召回
      ↓
定位 Chunk
      ↓
补充标题 / 相邻上下文
      ↓
完整 Context
      ↓
LLM
```

可以简单理解为：

> **小块负责“找得准”，大一点的上下文负责“看得懂”。**

# 5. 为什么最开始使用 FAISS？

简述：**检索算法本身是否有效。**

在验证检索策略时，我首先使用 FAISS 搭建本地检索原型。

流程非常简单：

```text
Document
   ↓
Chunk
   ↓
Embedding
   ↓
Vector
   ↓
FAISS Index
   ↓
Top-K Retrieval
```

这个阶段的重点不是搭建完整系统，而是快速验证一些核心问题：

```text
不同 Chunk 策略效果有没有差异？

Top-K 取多少比较合适？

Embedding 后能否召回正确文本？

加入 Rerank 后有没有提升？
```

FAISS 很适合这种快速实验。

因为此时真正关心的是：

> **检索算法本身是否有效。**

而不是服务部署、数据管理或者多用户访问。

# 7. 向量召回之后，为什么还需要 Rerank？

TODO 理解rerank的机制。

向量检索解决的是：

> 从大量文档中快速找到“可能相关”的候选文本。

但“可能相关”并不意味着排序一定准确。

例如用户的问题是：

> 数据资产登记需要满足哪些条件？

向量召回可能得到：

```text
1. 数据资产登记条件
2. 数据资产登记流程
3. 数据资产管理规范
4. 数据资产质量评价
5. 数据资产审核说明
```

这些文本都和问题相关。

但真正回答问题时，我们希望：

```text
真正包含“登记条件”的内容
```

排在最前面。

因此整体过程可以拆成两个阶段：

```text
Query
 ↓
Vector Retrieval
 ↓
Top-K Candidates
 ↓
Rerank
 ↓
Top-N Evidence
```

第一阶段更关注：

> **不要漏掉正确答案。**

第二阶段更关注：

> **把真正相关的证据排到前面。**

这也是为什么在实验过程中，我会对：

* Chunk 方式
* 召回数量
* Rerank 策略

进行对比，而不是只看一个向量模型的效果。

# 8. RAG 的真正难点：错误到底发生在哪一层？

在实际测试过程中，经常会遇到：

> 明明知识库里有答案，但系统就是答错了。

一开始很容易把所有错误都归因于“大模型幻觉”。

但真正分析以后，会发现错误来源完全不同。

我后来逐渐把 Badcase 按链路拆成几个部分。

## 8.1 文档解析问题

TODO 明确哪个多模态模型。

```text
原文有答案
↓
解析以后答案丢了
```

这时候需要检查 Parser，而不是修改 Prompt。

比如答案在图片里面，解析pdf的时候会把图片信息丢掉。

这里采取的方案是，结合上下文，使用**多模态模型**将图片里面的关键信息转文本描述。

---

## 8.2 Chunk 问题

```text
答案存在
↓
但是被切成几个不完整片段
```

这时候需要优化 Chunk 策略。

---

## 8.3 Retrieval Miss

```text
正确 Chunk 已经存在于向量库
↓
但没有进入 Top-K
```

这时候需要分析：

```text
Embedding
Top-K
Query 表达
检索参数
```

---

## 8.4 Ranking Error

```text
正确答案进入候选集
↓
但排名太低
↓
最终没有进入 LLM Context
```

这种问题更偏向 Rerank。

---

## 8.5 Context Missing

```text
找到了正确段落
↓
但是缺少标题或者前后文
```

这种问题就需要上下文补全。

---

## 8.6 Generation Error

还有一种情况是：

```text
证据已经完全正确
↓
但 LLM 仍然理解错误
```

这才真正进入生成阶段，需要考虑：

```text
Prompt
Context 组织
模型本身
```

因此我后来理解的 RAG Debug 流程更接近：

```text
问题答错
   ↓
原文有没有答案？
   ↓
解析结果有没有答案？
   ↓
正确 Chunk 有没有建立？
   ↓
有没有被召回？
   ↓
Rerank 后排第几？
   ↓
有没有进入最终 Context？
   ↓
LLM 是否正确使用了 Evidence？
```

而不是一看到结果错误就修改 Prompt。

实习经历：当时mentor让我将整个RAG链路罗列一个表格，针对每一条badcase，逐步核对表格每一个节点，以此来判定错误的具体位置在哪。

# 9. 用固定评测集验证，而不是凭感觉调系统

简述：RAG 优化必须建立在稳定 Evaluation Set 上，否则一次回答变好了，并不能证明系统真的变好了。

为了判断优化到底有没有效果，我们使用固定内部评测集进行验证。

整体实验过程可以抽象为：

```text
固定 Evaluation Set
        ↓
运行完整 RAG Pipeline
        ↓
得到回答
        ↓
按照统一标准评估
        ↓
统计结果
```

在这个过程中，主要围绕：

```text
Chunk Strategy
Retrieval Top-K
Rerank
Context
```

进行迭代。

最终在内部固定评测集上：

> **企业知识问答准确率达到 87%，较初始基线提升 18%。**

每次策略调整之后，都重新跑固定数据。

这样才能判断：

```text
到底是真的提升
```

还是：

```text
只是某几个 Case 恰好变好了
```

---

# 10. Badcase 才是推动 RAG 迭代的核心

简述：不要根据最终答案猜问题，而要沿着数据链路定位问题。

评测得到一个准确率以后，下一步并不是继续盲目调参数。

更重要的是分析剩下的错误。

例如有 100 个问题：

```text
87 个正确
13 个错误
```

真正值得研究的是：

> 剩下 13 个为什么错？

如果错误主要是：

```text
Retrieval Miss
```

那么继续优化 Prompt 几乎没有意义。

如果主要是：

```text
Context Missing
```

那么更值得优化 Chunk 与上下文补全。

如果主要是：

```text
Generation Error
```

才应该重点调整模型输入和生成策略。

所以我的工作逐渐形成了一个闭环：

```text
Evaluation
    ↓
Badcase
    ↓
错误分类
    ↓
链路定位
    ↓
策略修改
    ↓
重新 Evaluation
```

所以一定要做好日志管理机制，这也是我认为这段实习里最重要的工程思维之一：

> **不要根据最终答案猜问题，而要沿着数据链路定位问题。**

# 11. 从 RAG 到 MCP Tool

当检索能力逐渐稳定以后，它本身也可以被看成一个独立工具。


输入一个问题，返回：

```text
相关文档
相关 Chunk
来源信息
```

之后，我参与把知识检索、文档查询等能力通过 MCP 封装成工具，再接入已有 Agent 工作流。

整个关系可以简单理解成：

```text
Agent
  ↓
MCP Tool
  ↓
Knowledge Retrieval
  ↓
Milvus
  ↓
Enterprise Documents
```

这里 MCP 本身并不负责检索。

它更像是：

> **把已经实现好的检索能力，用统一方式暴露给 Agent。**

这样 Agent 不需要关心：

```text
Milvus 怎么查

Embedding 怎么算

Chunk 怎么组织
```

它只需要知道：

```text
我现在需要查询企业知识
↓
调用 Knowledge Tool
```

从工程角度看，这相当于把：

```text
RAG
```

从一段写死在业务代码里的逻辑，逐渐变成**可复用能力**。

进一步拆开，就是：

```text
企业文档
  ↓
解析和清洗
  ↓
结构化 Chunk
  ↓
FAISS 验证检索方案
  ↓
Milvus 承载向量数据
  ↓
Vector Retrieval
  ↓
Rerank
  ↓
Context 补全
  ↓
LLM Answer
  ↓
Evaluation
  ↓
Badcase Analysis
  ↓
继续优化
```

以及另一条业务接入链路：

```text
RAG Retrieval
      ↓
MCP Tool
      ↓
Agent Workflow
```

这两条线加起来，基本就是我这段实习工作的主体。

# 13. 最后：我从这段经历中真正理解了什么？

简述：**我做的并不是让大模型“知道更多”，而是让正确的企业知识能够在正确的时候，被可靠地找到并交给大模型。**

在真正做过一段 RAG 工作以后，我最大的感受是：

> **RAG 并不是“向量数据库 + 大模型”。**

一个能够稳定工作的 RAG 系统，更像是一条数据流水线。

任何一个环节出了问题：

```text
Parsing
Chunking
Embedding
Retrieval
Ranking
Context
Generation
```

最终都会表现成：

> “模型回答错了。”

但它们背后的原因完全不同。

所以相比于不停替换大模型，我现在更关注三个问题：

### 1. 正确的信息有没有进入系统？

对应：

```text
Parsing / Chunking
```

### 2. 用户提问以后，正确的信息有没有被找到？

对应：

```text
Retrieval / Rerank
```

### 3. 正确的信息被找到以后，模型有没有正确使用？

对应：

```text
Context / Generation
```

而 Evaluation 和 Badcase Analysis，能够判定：

> 问题到底出现在这三个阶段中的哪一个。

本报告依据科大讯飞实习简历条目进行还原，并以 TerminalTraj、Terminal-Bench、Harbor、SWE-agent、SWE-bench、Hugging Face TRL 与 Qwen3 官方资料作外部对照。采用三种标记：【已陈述】表示简历明确写出；【公开范式】表示可由公开技术资料验证，但不能直接视为个人实践；【待核实】表示关键工程细节或实验前提尚未由简历证明。文中的教学案例均为自拟，不包含企业真实代码、任务或私有数据。

## 02. 技术全景：Terminal Agent 究竟在学习什么

### 2.1 与普通 Code LLM 的关键区别

普通 Code LLM 往往针对一个静态输入直接产生代码文本；Terminal Agent 面对的是会因命令执行而改变的真实环境，必须反复执行“观察—决策—动作—反馈”。例如同一条安装命令可能因为依赖版本、权限或网络不同而产生完全不同的结果，模型下一步需要依赖实际输出，而非沿用预先编好的脚本。

可以将第 t 步抽象为：模型观察历史 h_t＝(任务说明、此前动作、此前工具反馈)，选择终端动作 a_t；沙盒执行后返回观测 o_t（stdout、stderr、exit code、文件系统副作用等），再形成 h_(t+1)。最终的成功标签通常来自任务对应的可执行测试，而非模型自行声明“完成了”。

由此，训练不仅是在学 Bash 语法，更是在学以下能力：任务分解与规划；工具接口遵循；解释 stderr；根据环境反馈纠错；验证工作是否完成；合理使用预算并停止。SWE-agent 的 ACI 研究证明，工具接口设计本身也会明显影响 Agent 表现，不能把 Harness 当成与模型无关的外壳。[R7]

### 2.2 为什么“环境 × 任务 × 测试”是一个不可拆开的单元

任务的自然语言描述本身，不足以构成一条可用的 Terminal Agent 训练样本。一个可信的任务实例至少需要：①初始环境和依赖能够落地；②任务指令明确且有足够信息；③存在可行的完成路径；④结果可以通过可执行测试判定；⑤交互行为能够被记录并在需要时回放。

TerminalTraj 明确将“可执行性、可验证性”定为规模化轨迹数据的两个瓶颈，并采用 Docker 环境、任务实例与可执行验证联合生成的范式。[R2] Terminal-Bench/Harbor 的任务结构也将 instruction、environment、solution 与 tests 分开组织。[R3][R4]

### 2.3 你所在的研究方向地图

| 技术层次 | 核心问题 | 与你实习的关系 |
|---|---|---|
| Task & Environment | 任务能否复现、运行、验证 | 任务格式统一、Docker 复现、Oracle/测试 |

## 03. 从原始任务到有效样本：全流程工程还原

### 3.1 第一关：任务标准化与来源治理

【已陈述】你处理的任务来源包含 TerminalTraj 等公开任务，以及团队已有任务。不同来源可能使用不同的字段名、文件布局、命令接口和评测逻辑。把它们转换为统一格式的目的，不是追求“JSON 长得一样”，而是让下游流程能够使用一致的输入契约启动、执行、验证和追溯。

【公开范式】建议把标准化单位定义为 Task Instance，其数据契约至少包含：task_id；source 与版本；instruction；workspace/初始文件；image 或 Dockerfile 版本与 digest；启动命令及约束；Oracle 入口；verifier 入口与版本；工具配置；时间/资源限制；train/eval split；任务授权/许可信息。企业内部实际字段需以真实代码为准。

为什么要记录 digest、版本和来源？因为“同一个任务今天能运行”不等于“下周能用相同环境重现”，而且训练数据如果无法回溯到来源、容器与测试版本，实验结果就难以归因。

关键质量检查：路径是否绝对且存在；依赖是否可安装；初始环境有没有预先携带答案；任务目标能否从描述中明确判断；测试是否泄露给 Agent；来自不同源的重复任务是否已去重；benchmark 题目是否混入训练。Terminal-Bench 官方任务模板明确区分 solution、tests 与 agent 环境，并设置防数据污染标记。[R3]

### 3.2 第二关：Docker 环境复现

【已陈述】你的核心贡献之一是复现约 2 千个任务中的运行环境。推荐面试时解释成四种递进状态，而不是笼统的“Docker build 成功”：
- 构建成功（Buildable）：镜像能构建，基础依赖齐备。
- 启动成功（Runnable）：容器可启动，任务工作目录、文件与权限正确。
- 参考可解（Solvable）：Oracle 在预期初始态能够完成任务。
- 验证可靠（Verifiable）：正确结果能稳定通过测试，错误结果不会轻易误过。

它们不是等价的：构建成功不保证任务有解；Oracle 运行结束也不等于所有任务要求得到满足；测试通过一次不等于测试稳定可靠。SWE-bench 官方 Harness 也采用容器构建、应用修改和测试判断组成可重复的端到端评测流程。[R8]

【公开范式】推荐保留失败原因标签：镜像构建失败、依赖冲突、网络不稳定、权限或工作目录错误、缺失数据文件、测试超时、Oracle 异常、测试非确定性。进一步区分“任务或环境本身不可用”和“Agent 无法解题”，否则后训练会被标签噪声污染。

### 3.3 第三关：Oracle 与 Verifier 分工

Oracle（参考解法）的作用主要是证明任务存在一条可行完成路径，并验证初始环境与任务定义基本合理。它并非唯一可行解，更不等于模型必须复现完全相同的命令顺序。Verifier（验证器）则检验任务要求是否得到满足：例如输出文件格式、服务是否可访问、测试是否通过、系统状态是否符合要求。轨迹回放进一步检验每一步记录是否与实际动作和工具输出匹配。

特别强调：exit code＝0 并不等于任务成功；模型最后说“已完成”也不等于任务成功；通过弱测试只能说明满足了测试检查到的约束。TerminalTraj 使用实例级可执行测试检测终态副作用，并把其视为过滤虚假成功轨迹的关键。[R2]

### 3.4 第四关：Teacher Agent 轨迹采集

【已陈述】你调用多种 Teacher 模型生成多轮交互轨迹，并处理成功、失败和错误恢复过程。一次完整的 Rollout 至少应该记录任务、模型与采样配置、每轮助手决策/工具动作、工具真实反馈、结束原因以及最终测试结果。

【公开范式】质量较高的采集管线应当保存五类信息：①来源与模型参数（Teacher 版本、temperature、seed）；②执行上下文（镜像版本、工具 API、时限）；③动作与反馈（命令、stdout、stderr、exit code）；④运行结果（终态测试、超时/异常）；⑤可追溯性（日志路径、轨迹 hash、任务来源）。这些是推荐做法，不代表你的团队都已实现。

在多 Teacher 环境中，不同模型的成功率、命令风格、恢复能力、轨迹长度和成本可能不同。不能简单地认定“大模型生成的轨迹一定优”，而应以执行结果和训练收益为核心比较。

### 3.5 第五关：从 Rollout 到 SFT 样本

一条 Agent Rollout 是交互记录，不自动等于能直接喂给模型的 SFT 样本。必须解决：工具消息的角色边界、动作与反馈一一对应、结束标识、异常输出清洗、截断导致的语义断裂、最终结果真假、重复轨迹以及训练标签所覆盖的 Token。

实践上建议把“任务和环境的有效性”与“轨迹是否值得训练”分成两层门禁。前者解决环境噪声；后者解决行为监督质量。过滤掉不可用环境，不应被误记为提高了 Teacher 的策略成功率。

## 04. 轨迹质量：为什么最后通过测试仍然可能是坏数据

### 4.1 建议采用的轨迹质量分桶

| 分桶 | 典型特征 | 推荐处理 |
|---|---|---|
| A：高质量成功 | 终态通过测试；动作—反馈一致；验证步骤完整 | 优先纳入正向 SFT |
| B：带恢复的成功 | 中途出现真实错误；能根据反馈正确恢复；终态通过 | 保留恢复价值，审慎处理错误动作标签 |
| C：低效但成功 | 终态成功，但重复命令多、无效探索多 | 降权或另行采样；不只看是否通过 |
| D：失败但可诊断 | 工具错误、误判反馈、循环、超时等 | 用于 Badcase、诊断或专门负反馈构造 |
| E：不可信轨迹 | 伪造反馈、跨轮错位、泄露答案、测试不稳定 | 排除或修复后重验 |

本表属于【公开范式建议】，不是对你内部正式分桶体系的断言。建议面试时用自己真实遇到的一类 Badcase 展开，而非把全部分桶说成你独立提出。

### 4.2 三个不能混淆的“质量”

- 结果质量：是否真正通过可靠测试。
- 过程质量：工具调用是否合法，是否尊重先前反馈，是否出现无效重复与自我矛盾。
- 监督质量：被计算 Loss 的 Token 是否代表我们希望学生模型学习的行为。

一条成功轨迹有可能包含无效命令，如果对所有助手动作直接计算 Loss，错误动作同样可能被模仿。因此“最终成功”是重要门槛，但不足以保证每一个被监督的局部决策都正确。另一方面，带错误恢复的成功轨迹也可能包含独特价值，能训练模型在看到 stderr 后做出合理的后续动作。

### 4.3 轨迹回放要检查的关键一致性

逻辑上，每条动作应产生与该执行状态相符的反馈；后续助手判断必须基于它真正看到的反馈。典型不一致包括：上一轮命令失败，下一轮却说已成功；工具输出被摘要时漏掉关键报错；把另一条 Rollout 的 stdout 拼接进当前轨迹；测试在不同初始状态下回放；日志顺序与执行顺序不一致。

因此，回放不仅用于复核最终正确性，还可发现“文本看似流畅，但状态转换并不真实”的样本。真正值得保留的是可供模型学习的因果链条，而非貌似合理的聊天记录。

### 4.4 自动验收与人工抽检怎样结合

【公开范式】推荐先进行低成本硬门禁：环境可启动、格式合法、命令和观测配对正确、最终测试通过、敏感信息检查、去重。再对高价值或可疑样本做人审/二级分析：异常恢复、偏长轨迹、反常通过、测试覆盖不足、Teacher 间结论冲突。

TerminalTraj 在公开实验里对比“仅让模型判断是否成功”与“执行代码验证是否成功”的轨迹筛选策略，后者用于 SFT 的模型表现更好。这支持执行验证的价值，但不是你个人 4.2 个百分点增益的独立归因结果。[R2]

## 05. SFT 技术核心：Loss Mask 到底在改变什么

### 5.1 多轮轨迹 SFT 的数学对象

给定拼接后的 token 序列 x_1,…,x_T，SFT 通常最小化负对数似然。引入 mask 后可写成：

L(θ) = − [Σ_t m_t · log Pθ(x_t | x_<t)] / [Σ_t m_t]，其中 m_t ∈ {0,1}。

m_t＝1 表示该 token 参与监督；m_t＝0 表示它虽然可能作为上下文出现，但不直接作为训练目标。具体实现中，很多框架会通过 labels＝−100 忽略被 mask 的 Token。Hugging Face TRL 公开文档支持 assistant-only loss，以及对工具调用对话的数据格式。[R5]

请牢牢记住：**被 mask 的工具输出依然可以供模型理解与条件化；mask 只决定是否要求模型预测它。** 在 Agent SFT 里，工具反馈一般是外部环境事实，而非助手主动要生成的内容。

### 5.2 三种需要区分的设计

方案 A：只训练 Assistant 响应。对 user/system/tool 消息不算 Loss，助手的工具调用、回复则作为监督目标。这是最直观的 Agent SFT 方案之一。

方案 B：更细粒度地监督助手行为。若数据含显式思考、动作调用与自然语言总结，可以研究只监督可执行动作和最终答案、对部分思考或不可靠片段作 Mask。该方案必须和 Qwen3 的 chat template 与 thinking 模式兼容，不能直接删除特殊标记后假设模型仍能正确学习。

方案 C：全对话或异常 Mask 设置作为对照。若连 tool 输出也被预测，模型可能花大量容量去拟合环境日志而不是学习决策；但是否一定降低最终成绩，仍需实验，不应把机制推测当作你已有结论。

### 5.3 错误恢复数据的特殊处理

要区分“错误环境反馈”和“错误助手行为”。看到失败命令后给出有效排查动作，是优秀的监督；但导致失败的无效命令未必值得继续作为正向目标。如果原始成功轨迹包含错误命令，可尝试局部 Mask 错误动作、构造从错误反馈开始的恢复片段，或将其放入专门对照组。所有这些都是【可检验方案】，需要实际 tokenizer 与数据处理实现来判断可行性和收益。

对纯失败轨迹，通常不宜直接把失败全过程当作“应该生成的正确答案”参与普通正向 SFT；它可以用于失败分析、对比/偏好数据、恢复训练或过滤器训练。这些用途的目标函数并不相同。

### 5.4 Qwen3-8B 的格式注意事项

Qwen3-8B 官方提供 thinking 与 non-thinking 模式切换，并使用特定 chat template。决定如何处理思考段、工具消息、EOS 与 Loss Mask 时，训练模板与推理 Harness 的格式一致性非常重要。[R6]

【待核实】你的实验中到底用了 thinking 还是 non-thinking 模式？工具调用是函数调用 JSON、专用工具协议，还是文本终端动作？Loss Mask 的具体对照是哪几组？没有这些信息，面试中不要擅自说“我们只训练了 action token”或“我们把 reasoning 全 mask 了”。

## 06. 实验设计：把“跑出结果”变成“能说清因果”

### 6.1 简历结果能说明什么，不能说明什么

【已陈述】固定 Agent Harness 的条件下，向 Qwen3-8B 的增量 SFT 数据中加入你负责构建的有效轨迹，Terminal 任务完成率从 3.7% 上升到 7.9%。

能说：在简历所描述的实验设置下，加入这一批有效轨迹的训练配置，报告的端到端任务完成率更高。

目前不能单凭简历断言：提升完全由“质量筛选”产生；特定 Teacher 或某种 Mask 单独贡献多少；评测结果具有统计显著性；提升可在其他任务集、Harness、随机种子下稳定重现；模型已经达到公开 Terminal-Bench 某个版本的同等水准。

尤其是不能把论文或其他公司的公开 benchmark 分数与这组结果直接对比，因为任务集版本、运行框架、采样预算和模型基座可能完全不同。

### 6.2 面试官最可能追问的控制变量

要想把这组结果讲成一个可靠的 A/B 实验，必须说明 A/B 两组是否使用相同基础模型 Checkpoint、相同任务与训练/测试隔离方式、相同 SFT 超参、相同训练 Token 或 steps、相同 tokenizer 和 chat template、相同 Harness/Prompt、相同工具预算与超时、相同 sampling 设置与评价次数。

简历只明确写出了“固定 Agent Harness”。其余条件建议根据原始实验配置补齐。没有日志就说“尚需进一步核对”，而不是根据经验臆造学习率、LoRA rank、batch size、epoch 或显卡数量。

### 6.3 推荐的逐层消融矩阵（实验建议，非个人已完成清单）

| 对照组 | 改动因素 | 要回答的问题 |
|---|---|---|
| E0：Baseline | 不加入新增轨迹 | 原始基础能力是多少 |
| E1：Valid-Traj | 加入通过执行验证的轨迹 | 新轨迹总体是否有效 |
| E2：Quality-Matched | 样本/Token 规模相同，改变质量门槛 | 质量而非数量是否有效 |
| E3：Teacher-Matched | 固定规模和难度，只换 Teacher 来源 | Teacher 多样性或质量是否有收益 |
| E4：Recovery | 同等规模下加入/移除恢复片段 | 学会纠错是否改善完成率 |
| E5：Loss Mask | 数据相同，只换监督目标 | 哪种监督位置更有效 |
| E6：Difficulty Mix | 同等 Token 预算，改变难度分布 | 简单/困难样本该如何配比 |

这里有个常见实验陷阱：如果质量高的组同时 Token 更多或训练步数更长，观测到的提升就不能简单归因于质量门槛；如果 Teacher 组的数据难度分布不同，也不能把差异全归因于 Teacher 本身。

### 6.4 如何统计 Terminal 任务完成率

最基础的是 task-level success rate＝通过终态测试的任务数 / 被评测任务数。但真实 Agent benchmark 还必须声明 pass@1、pass@k、是否允许多次尝试、失败超时是否计入分母、是否按任务或按 Rollout 计数。

评测最好报告版本与任务数、独立重复实验、平均值及置信区间，以及关键失败类别。TerminalTraj 公开论文通过多次独立评测和置信区间控制结果解释范围，并展示 pass@k 对测试时采样预算的敏感性。[R2]

注意：你的简历目前未提供评测集总数，所以不能仅凭 3.7% 和 7.9% 推导出成功任务的绝对数量或统计显著性。

## 07. 失败类型与排障：如何体现你的技术判断力

建议把 Badcase 拆分为四层，避免把所有失败都归给“模型能力差”。

第一层：任务/环境失败。依赖装不上、Docker 镜像不可复现、初始文件缺失、Oracle 不可执行、测试自身不稳定。处理方向：环境修复、重构任务、剔除不可信实例。

第二层：接口/轨迹失败。工具格式错误、stderr 丢失、动作与输出错位、日志截断、长任务状态丢失。处理方向：规范 Tool Schema、重放审计、增强 Harness 观测和状态保存。

第三层：模型策略失败。忽略报错、重复无效命令、不会验证成果、错误估计权限/依赖、长任务迷失。处理方向：补充高质量失败恢复轨迹、难度/场景配比和针对性监督。

第四层：训练/评测失败。训练样本污染评测任务、Mask 位置错误、chat template 不一致、超时或采样预算变化、实验种子造成波动。处理方向：控制变量、独立验证和实验审计。

CAMEL SETA 研究特别指出，终端任务要求控制长时运行进程、接受实时反馈、维护长任务状态，其工具接口设计和环境覆盖均可能显著影响表现。[R9] 这也是为什么只讲“数据量”远远不够。

## 08. 教学案例：一条可学习的恢复轨迹是怎样形成的

以下案例完全是教学示意，不是科大讯飞真实任务或内部日志。

任务：容器中已有 /workspace/data/orders.csv，要求把各状态的订单金额汇总写入 /workspace/out/summary.json，并通过任务测试。Agent 可以在终端执行命令，但不知道初始文件布局是否完全符合预期。

步骤一：Agent 直接运行处理脚本，工具返回“输出目录不存在”或类似错误。此时它虽然尚未完成任务，但产生了可观测的真实失败反馈。

步骤二：Agent 读取错误原因，检查 /workspace/out 的父路径，确认是目录缺失，而不是 CSV 文件内容损坏。这个判断必须依赖实际 stdout/stderr，而不是凭空猜测。

步骤三：Agent 创建目标目录，重新运行处理程序，再使用任务允许的自检命令检查输出文件存在、结构和统计值符合需求。

步骤四：终态验证器在独立环境或受控权限下执行自动测试，确认结果达到任务标准。采集程序据此标记 Rollout 的最终状态。

这段数据中真正值得模仿的部分是“识别出错误原因 → 定位状态 → 修复问题 → 再验证”的闭环。若把第一步错误命令也无差别当作理想动作，可能引入不必要的监督噪声；是否局部 Mask、如何拆分恢复片段，应由真实训练对照实验检验。

### 如何把这个案例映射到你工作中的三道验证

1. 任务层：Oracle 能否完成汇总，Verifier 能否区分正确与错误 JSON？
2. 轨迹层：工具反馈是否是真实运行得到的；Agent 后续动作是否以此为依据？
3. 训练层：哪些助手 Token 参与 Loss；是否保留恢复阶段；是否对长轨迹执行有损截断？

这三个问题分别对应“可解性”“行为可信度”“监督有效性”，是深入讨论 Terminal Agent 训练数据时最值得强调的技术分层。

## 10. 面试表达：从“做了什么”升级为“解决了什么问题”

### 10.1 90 秒版：适合面试开始时讲项目

“我在科大讯飞词元星火研究部主要做 Terminal Agent 的训练数据和评测。这个方向与普通代码生成不同，模型要在真实命令行环境中连续执行任务，并根据每一步 stdout、stderr 等反馈调整后续动作。我们遇到的主要难点是任务环境难复现、Teacher 生成的轨迹质量不稳定，以及轨迹能不能真正提供有效监督信号。

我负责的工作可以概括为三块：首先将 TerminalTraj 等任务数据整理成统一格式，用 Docker 复现环境，并用 Oracle、任务测试和回放检查任务能否执行与验证；其次用不同 Teacher 模型采集多轮轨迹，针对最终成功与否、动作反馈一致性、验证完整性、错误恢复等维度清洗筛选；最后参与 Qwen3-8B 的增量 SFT 和固定 Harness 评测，分析 Teacher、样本难度、数据配比和 Loss Mask 对训练效果的影响。

在团队约三万条终端 SFT 数据建设中，我负责约两千个任务的处理闭环。简历记录的对照实验中，加入我负责构建的有效轨迹后，Terminal 任务完成率由 3.7% 提升至 7.9%。这段经历让我认识到，Agent 数据的核心不是只看生成文本像不像答案，而是必须保证环境真实可运行、结果可验证，并让模型真正学会根据反馈进行下一步决策。”

这段话不主动认领超出简历的技术实现，适合作为可进一步展开的基础版本。

### 10.2 三分钟版的结构，不要一口气堆技术名词

按“背景与痛点 → 你负责的闭环 → 最难的质量问题 → SFT 对照 → 结果与局限”的顺序讲。

背景：Terminal Agent 需要可执行闭环，不能用仅有问答的 SFT 数据替代。职责：你负责约两千个任务的环境—轨迹—验证—数据落盘。技术难点：环境真假、通过真假、动作与反馈一致、失败恢复是否可学。验证：固定 Harness，对不同训练数据与 Mask 设置做对照。结果：报告 4.2 个百分点提升；严谨补充评测口径和未识别的混杂因素。

### 10.3 面试官高频追问与回答要点

问：为什么不直接使用公开轨迹数据训练？
答：不同任务的依赖、初始状态和测试口径不一致；轨迹文本流畅也可能没有真实执行依据。要先完成格式统一、环境复现、可解性和终态验证。

问：Oracle 和测试脚本到底有什么区别？
答：Oracle 提供已知可行路径以验证任务基本可解；Verifier 判断终态是否满足要求，不应要求与 Oracle 命令逐字相同；轨迹回放补充过程一致性。

问：为什么成功轨迹也要筛选？
答：成功可能是偶然或测试覆盖不足；过程可能冗长、忽略反馈甚至出现错误动作。被监督的每个 token 是否有教育意义，与最终是否成功不是完全相同的问题。

问：失败轨迹能用来 SFT 吗？
答：最终失败的整条轨迹不能默认当作正确示范；但失败后的正确恢复行为可能很有价值。需要区分“失败事实作为上下文”和“错误动作作为标签”，再设计 Mask/片段/其他目标函数。

问：Loss Mask 的作用是什么？
答：控制哪些 token 产生梯度。工具返回的 stdout/stderr 可以保留为条件上下文，但通常不应当作模型需要生成的目标；助手动作和最终答复则是常见监督目标。

问：为什么要固定 Harness？
答：Harness 包含提示词、工具接口、执行预算、反馈格式等，会显著改变 Agent 表现。如果同时改变 Harness 和模型训练数据，无法清楚判断提升来自哪里。

问：你如何证明提升来自高质量数据而不是数据量？
答：理想上做相同 Token/样本预算下的质量对照，并固定基础模型、超参、评测协议。现有简历能证明新增有效轨迹的实验配置报告了更高完成率；质量策略的独立因果效应需要查看消融日志。

问：2 千个任务和 3 万条数据是什么关系？
答：前者是个人处理的 task 实例数量，后者是团队 SFT 数据规模，单位不同；一个任务可能产生多条 Rollout，也可能没有合格轨迹，不能直接进行份额换算。

问：为什么 3.7% 到 7.9% 的绝对分数仍然不高？
答：复杂终端任务端到端成功需要多个步骤都正确；小模型、任务难度、工具设计和预算均可能形成瓶颈。重点应解释任务集难度、基线条件、可重复提升及失败机制，而不是仅讨论分数大小。不能用不同 benchmark 上的公开结果直接为内部低分作证明。

问：如果重新做一遍，你优先改什么？
答：先建立任务级数据谱系和分层质量漏斗，再在等 Token 预算下研究恢复轨迹、Teacher 组成及 Mask；同时保留独立 eval split、重复评测和失败类别统计，提升结果的可解释性。

## 11. 必须从真实材料补齐的“证据清单”

以下问题的答案最好来自你当时的实验表、配置文件、日志或同事共享文档，而不是事后推测。

【任务数据】任务来自 TerminalTraj 的哪个版本？其余来源有哪些？是任务数量还是独立环境数量？标准格式字段是什么？如何识别重复、污染与不合法任务？

【环境】构建失败和 Oracle 失败分别如何处理？Dockerfile/镜像版本如何固定？Oracle 和测试是否隔离？Verifier 是否复跑以检测偶发通过？

【Rollout】Teacher 的具体模型和版本有哪些？每题采集多少次？使用什么 Harness、工具协议、停止条件、超时和最大步数？stdout/stderr 如何保存？“轨迹回放”是全文本校验还是真实重新执行？

【样本】哪些失败轨迹进入训练、哪些只是分析？质量分桶规则到底是什么？去重在任务级还是轨迹级？两千任务最终产出多少合格轨迹、多少有效训练 Token？

【训练】Qwen3-8B 的具体 checkpoint、full fine-tune 还是 LoRA/QLoRA？优化器、学习率、batch、sequence length、epoch/steps、有效 Token 预算？是否启用 thinking？工具消息与 reasoning 的 Loss Mask 精确定义是什么？

【评测】Terminal 任务完成率对应哪个内部或公开评测集、具体版本、任务数、计分方式、运行次数与采样设置？3.7% 与 7.9% 是否在完全相同的条件下评估？是否有任务级成功列表和典型 Badcase？

把这些补齐后，实习报告就能从“基于简历的技术复盘”升级成“可审计的实验复盘”。在此之前，对尚未确认的指标和算法实现保持准确边界，是面试可信度的重要一部分。

## 12. 建议的学习与复习顺序

第一阶段：彻底理解 Task—Environment—Oracle—Verifier 的关系。通读 Terminal-Bench 的任务格式和 TerminalTraj 的数据构造部分，尝试为一个公开的小任务画出初始化、执行、终态测试的生命周期。

第二阶段：彻底理解多轮轨迹和监督目标。把一条 Rollout 划分为 user、assistant tool call、tool observation、assistant final 四类内容，明确哪些 token 作为上下文、哪些参与 Loss，并特别关注错误恢复片段。

第三阶段：彻底理解实验归因。自己写一张控制变量表，对所有已跑过的 SFT 配置标注：训练数据规模/来源/难度/Mask、训练预算、推理 Harness、成功率和失败分类。

第四阶段：训练面试表达。准备一个能脱敏的真实任务案例，严格沿“原始问题—遇到的报错—诊断与解决—自动验证—进入训练的数据形式—实验结果”讲述。真正说清一个案例，比罗列十个框架名称更能证明你做过技术工作。

## 13. 最终结论

你实习工作的独特性不是“知道 Terminal Agent、会用 Docker、会跑 SFT”三个孤立技能，而是对 Agent Post-training 的数据可信链条有实践：**让任务真的能运行，让轨迹真的对应环境，让结果真的能验证，让模型的监督信号尽可能来自可靠行为，再用受控评测检查其有效性。**

对下一段日常实习的求职定位，建议优先使用“Agent 训练数据与评测”“Agent 后训练 / SFT 数据质量”“Terminal / Code Agent 数据与环境工程”等关键词。若目标岗位更偏算法研究，应重点展开 Loss Mask、质量消融、Teacher 采样与分桶分析；若更偏 Agent 应用/框架，则优先强调 Docker 复现、工具交互、轨迹回放、执行验证和评测可复现性。

# Day 12｜DeepSeek-R1：为什么只奖励答案正确，模型就能学会反思？

> **核心关键词**：DeepSeek-R1、R1-Zero、Reinforcement Learning、Reward、RLVR、RLHF、GRPO、Long CoT、Reflection、Verification
>
> **本文目标**：不背 Benchmark，不纠结模型参数，而是从训练原理出发，理解 DeepSeek-R1 为什么重要，以及它揭示了什么关于大语言模型推理能力的规律。

## 一、引言：DeepSeek-R1 真正值得关注的是什么？

提到 DeepSeek-R1，很多人的第一反应可能是：

* 它的数学能力很强。
* 它能生成很长的推理过程。
* 它会说“等等，我需要重新检查一下”。
* 它在一些推理任务上表现出色。

但这些都是我们观察到的**结果**。

真正值得研究的问题是：

**为什么模型能够学会这些行为？**

过去，一种增强模型推理能力的常见思路是：先让人类专家编写高质量推理过程，再通过监督微调（Supervised Fine-Tuning，SFT），让模型学习这些示范。

例如，面对一道数学题：

```text
问题：解方程 2x + 6 = 14

人类提供的推理示范：

Step 1：两边同时减去 6
        2x = 8

Step 2：两边同时除以 2
        x = 4

Final Answer：4
```

模型通过学习大量这样的数据，逐渐掌握生成分步解题过程的能力。

但是，这种方法存在一个问题：

**如果想让模型学会更复杂的推理，我们就需要提供大量高质量的推理示范。**

而复杂推理示范往往需要专家编写，成本较高，也可能限制模型探索其他有效的解题方式。

DeepSeek-R1-Zero 尝试了一条不同的路线：

> 不提前通过 SFT 教模型应该如何一步步推理，而是让它自己探索解题方式，并通过强化学习奖励能够得到正确答案的行为。

研究人员发现，在这样的训练过程中，模型逐渐表现出自我检查、反思、尝试其他解法以及更长的推理过程等行为。

这一研究后来以 *DeepSeek-R1 incentivizes reasoning in LLMs through reinforcement learning* 为题，于 2025 年 9 月正式发表于 Nature。[1]

**这篇论文最重要的意义，并不是证明模型能够输出很长的推理文本，而是展示了：在具有可靠奖励信号的任务上，强化学习能够激励模型发展出更复杂的推理行为。**

## 二、先理解 Reward：模型究竟是怎么被奖励的？

在理解 DeepSeek-R1 之前，需要先理解强化学习中最核心的概念之一：Reward（奖励）。

### 2.1 Reward 是什么？

简单来说：

**Reward 是一个评价信号，用来告诉模型当前生成的结果有多好。**

假设我们正在训练一个模型解决数学题。

问题是：

```text
2x + 6 = 14
```

模型可能生成不同的回答。

**回答 A：**

```text
2x + 6 = 14
2x = 8
x = 4

答案：4
```

**回答 B：**

```text
2x + 6 = 14
2x = 8
x = 4

检查：
2 × 4 + 6 = 14

验证正确。

答案：4
```

**回答 C：**

```text
2x + 6 = 14
2x = 20
x = 10

答案：10
```

假设我们使用最简单的正确性奖励：

$$
R_{\text{accuracy}} =
\begin{cases}
1, & \text{最终答案正确}\\
0, & \text{最终答案错误}
\end{cases}
$$

那么：

| 回答 | 最终答案 | Accuracy Reward |
| -- | ---- | --------------- |
| A  | 4    | 1               |
| B  | 4    | 1               |
| C  | 10   | 0               |

这里有一个非常重要的细节。

**回答 B 多进行了一次检查，但并没有因为“检查这个动作”而获得额外的正确性奖励。**

只要最终答案正确，A 和 B 都可以得到相同的 Accuracy Reward。

这意味着奖励函数并没有明确要求模型：

* 必须进行反思。
* 必须检查答案。
* 必须使用某种特定解法。
* 必须生成很长的推理过程。

它主要关心的是：

**最终有没有解决问题。**

### 2.2 模型如何利用 Reward 学习？

我们可以把强化学习过程简化为：

```text
                  输入问题
                     │
                     ▼
                  LLM Policy
                     │
                     ▼
               生成候选回答
                     │
                     ▼
               Reward Function
                     │
             ┌───────┴───────┐
             │               │
          高 Reward       低 Reward
             │               │
             ▼               ▼
       强化相关行为      降低相关行为
             │               │
             └───────┬───────┘
                     │
                     ▼
                 更新 Policy
                     │
                     ▼
                下一轮训练
```

这里的 Policy（策略）就是模型在给定问题后，生成不同 Token 序列的概率分布。

强化学习希望提高模型的期望奖励：

$$
\max_\theta
\mathbb{E}_{x\sim D,\ y\sim\pi_\theta(\cdot|x)}
[R(x,y)]
$$

其中：

* \(x\)：输入的问题。
* \(y\)：模型生成的回答。
* \(\pi_\theta\)：模型当前的生成策略。
* \(R(x,y)\)：回答获得的奖励。
* \(D\)：训练问题的分布。

这个公式不用死记。

它表达的核心思想非常简单：

> **让模型在未来生成回答时，更倾向于采用那些能够提高预期奖励的行为。**

当然，实际的强化学习更新比“正确答案加分，错误答案减分”复杂得多。

DeepSeek-R1 使用的具体算法是 GRPO，我们稍后会介绍。

### 2.3 R1-Zero 的 Reward 设计

根据 DeepSeek-R1 的正式论文，R1-Zero 主要采用规则型奖励（Rule-based Rewards），包括：

**Accuracy Reward（正确性奖励）**

判断模型是否得到了正确答案。

例如：

* 数学题最终答案是否正确。
* 代码是否通过预定义测试。
* 某些逻辑推理任务的结果是否符合可验证规则。

**Format Reward（格式奖励）**

判断模型是否按照要求输出。

例如，要求模型使用特定标签组织推理过程：

```xml
<think>
这里是推理过程
</think>
```

论文中的规则奖励可表示为：

$$
R_{\text{rule}}=R_{\text{accuracy}}+R_{\text{format}}
$$

因此，准确地说，R1-Zero 并不是完全只奖励最终答案。

它还使用格式奖励，但**没有使用人工标注的逐步推理轨迹来规定模型每一步应该如何思考**。[1]

这也是我们理解后面 reasoning behavior 出现的前提。

### 2.4 用 Python 实现一个简化版 Reward

为了直观理解奖励函数，可以自己写一个非常简化的 Verifier。

这里假设模型必须使用 `<answer>` 标签输出最终答案，而格式奖励还要求它提供 `<think>` 标签。

> 说明：下面是教学示例，不是 DeepSeek 官方训练代码。`<answer>` 是为了方便演示而设计的输出格式。

```python
import re


def toy_reward(response: str, gold: str) -> dict[str, int]:
    # 提取末尾的最终答案
    match = re.search(
        r"<answer>\s*([^<>]+?)\s*</answer>\s*\Z",
        response,
        re.S,
    )

    accuracy = int(
        match is not None
        and match.group(1).strip() == gold.strip()
    )

    # 检查推理与答案的整体格式
    well_formed = re.fullmatch(
        r"\s*<think>.+?</think>\s*<answer>\s*[^<>]+\s*</answer>\s*",
        response,
        re.S,
    ) is not None

    format_score = int(well_formed)

    return {
        "accuracy": accuracy,
        "format": format_score,
        "total": accuracy + format_score,
    }


# 答案和格式都正确
assert toy_reward(
    "<think>2x = 8，所以 x = 4</think><answer>4</answer>",
    "4",
)["total"] == 2

# 答案错误，但格式正确
assert toy_reward(
    "<think>我算出了 x = 5</think><answer>5</answer>",
    "4",
)["total"] == 1

# 答案正确，但缺少推理格式
assert toy_reward(
    "<answer>4</answer>",
    "4",
)["total"] == 1

# 没有有效答案
assert toy_reward(
    "<think>还没有计算出答案</think><answer></answer>",
    "4",
)["total"] == 0
```

这个例子非常简单，但足够说明：

**Reward 可以由程序自动生成，不一定要人工逐条评价模型的回答。**

不过，这个简化实现也暴露了一个问题。

假设正确答案是 `4`，模型输出 `04`，两者在数学意义上相等，但是字符串比较可能判错。

所以真实的数学 Verifier 往往需要进行答案提取、格式归一化或数学等价性判断。

这也为理解 RLVR 的局限埋下了伏笔。

## 三、为什么数学和 Code 特别适合 RLVR？

现在引入 DeepSeek-R1 背后非常重要的概念：

**RLVR（Reinforcement Learning with Verifiable Rewards）——基于可验证奖励的强化学习。**

RLVR 的核心思想是：

> 如果一个任务的结果能够被可靠地自动验证，那么就可以利用这个验证结果产生奖励信号，训练模型学习更好的解决策略。

这里有一个值得记住的判断：

**一个任务可能很难解决，但它的答案却相对容易验证。**

也就是：

> Solving is hard, but verification can be easy.

### 3.1 数学为什么适合？

例如：

```text
问题：求解一个复杂的数学问题。
```

模型可能需要：

```text
理解题目
   ↓
尝试解法 A
   ↓
发现不适用
   ↓
尝试解法 B
   ↓
进行推导
   ↓
得到答案
```

整个求解过程可能非常复杂。

但是，如果题目具有明确、可自动检查的标准答案，那么验证过程可能只需要：

```text
模型最终答案
     ↓
答案提取和归一化
     ↓
与标准答案比较
     ↓
Correct / Incorrect
```

因此，即使我们没有模型每一步推理的标准示范，也可以对最终结果提供奖励。

但并不是所有数学任务都能轻松验证。例如开放性证明题、自然语言证明以及难以形式化的问题，可能需要更复杂的验证机制。

### 3.2 代码为什么适合？

代码任务也是类似的逻辑。

假设我们要求模型实现一个函数：

```text
实现 is_palindrome(s)，判断字符串是否为回文。
```

我们可以预先定义测试：

```python
assert is_palindrome("aba") is True
assert is_palindrome("abc") is False
assert is_palindrome("a") is True
assert is_palindrome("") is True
```

模型生成代码之后，训练系统可以运行测试，并将结果转换成 Reward。

```text
            Coding Problem
                  │
                  ▼
              LLM 生成代码
                  │
                  ▼
            执行测试用例
                  │
           ┌──────┴──────┐
           │             │
       Tests Pass    Tests Fail
           │             │
           ▼             ▼
       High Reward    Low Reward
```

这意味着，我们并不一定需要人工检查每一份生成的代码。

只要测试环境足够可靠，就可以规模化提供反馈。

当然，**通过测试不等于程序完全正确**。

测试覆盖不完整、边界条件遗漏、运行环境不一致，都可能使 Verifier 给出不准确的评价。

### 3.3 为什么开放式写作更困难？

再考虑另外一种任务：

```text
请写一篇优美、富有感染力的短文。
```

现在如何设计 Reward？

我们可能希望文章：

* 有创意。
* 表达自然。
* 情感真挚。
* 结构清晰。
* 符合读者偏好。

但这些标准很难用简单的确定性规则判断。

即使有两篇文章，人类也可能对哪篇更好产生分歧。

因此，对于这类任务，通常需要人类偏好反馈，或者借助经过训练的 Reward Model 进行评价。

这就涉及传统 RLHF。

### 3.4 关键差异不是任务难度，而是可验证性

| 任务类型      | 典型验证方式        | 主要困难          |
| --------- | ------------- | ------------- |
| 有标准答案的数学题 | 答案匹配、数学等价性检查  | 答案提取与等价判断     |
| 算法编程题     | 编译、运行、单元测试    | 测试覆盖不充分       |
| 形式化证明     | Proof Checker | 需要形式化表达       |
| 事实问答      | 可信数据源、事实核验    | 信息歧义和时效性      |
| 创意写作      | 人类偏好、模型评价     | 主观性强，难以确定唯一标准 |

所以 RLVR 的关键不是：

“数学和代码比写作重要。”

而是：

**数学和代码中的某些任务，更容易构造可靠、自动化、成本可控的奖励机制。**

当 Verifier 足够可靠时，我们可以在较少依赖人工逐条标注的情况下，持续生成强化学习信号。

这正是 RLVR 具有吸引力的原因。

## 四、R1-Zero：不先教推理过程，直接进行 RL

理解了 Reward 和 RLVR，就可以进入 DeepSeek-R1-Zero 的核心实验。

### 4.1 R1-Zero 的训练思路

R1-Zero 的训练起点是已经预训练过的 **DeepSeek-V3-Base**。

研究人员跳过了强化学习之前通常使用的 reasoning SFT 阶段，直接对 Base Model 进行大规模强化学习。[1][2]

训练流程可以简化成：

```text
           DeepSeek-V3-Base
                    │
                    ▼
             输入推理问题
                    │
                    ▼
             生成多个候选回答
                    │
                    ▼
             Rule-based Reward
                    │
              ┌─────┴─────┐
              │           │
         Accuracy       Format
              │           │
              └─────┬─────┘
                    │
                    ▼
               GRPO 更新
                    │
                    ▼
             改进模型策略
                    │
                    ▼
              DeepSeek-R1-Zero
```

这里需要澄清一个经常被误解的问题：

**R1-Zero 的 Pure RL，不代表模型完全没有预训练，也不代表整个系统没有人工设计。**

它仍然需要：

* 一个已经具备大量语言和知识基础的 Base Model。
* 训练问题和参考答案。
* 人工设计的输出格式。
* 可靠的 Reward Function。
* 强化学习训练算法和计算资源。

所谓 Pure RL，主要强调的是：

**在该 reasoning 强化学习阶段之前，不依赖额外的监督微调推理示范作为冷启动。**

这是一个非常重要的区别。

### 4.2 GRPO 在这里起什么作用？

R1-Zero 使用的强化学习算法是 **GRPO（Group Relative Policy Optimization）**。

GRPO 最早在 DeepSeekMath 研究中被提出。[4]

不展开完整优化公式，我们只理解它的核心直觉。

假设对于同一道问题，模型采样出多个回答：

```text
                 Question
                    │
          ┌─────────┼─────────┐
          │         │         │
          ▼         ▼         ▼
       Answer A  Answer B  Answer C
          │         │         │
          ▼         ▼         ▼
        Reward    Reward    Reward
          │         │         │
          └─────────┼─────────┘
                    │
                    ▼
           组内相对奖励比较
                    │
                    ▼
              更新模型策略
```

GRPO 的核心是根据同一道题的一组候选回答的 Reward，计算它们的相对优势（Advantage）。

直观理解：

* 组内奖励相对较高的回答，对策略更新提供正向信号。
* 组内奖励相对较低的回答，提供负向信号。
* 模型逐渐提高生成有利于获得较高奖励的回答的概率。

GRPO 的一个重要特点是，它不需要像传统 PPO 的某些实现那样，额外训练独立的 Value Model 来估计 Advantage，而是利用组内奖励构造相对优势。

注意：GRPO 是一种**优化算法**，RLVR 是一种**奖励信号设计思路**。

它们不是相互替代的概念。

可以这样理解：

> RLVR 回答“用什么信号评价结果”，GRPO 回答“如何利用奖励更新模型”。

## 五、为什么模型会出现 Reflection、Verification 和 Long CoT？

这是整篇文章最值得深入思考的部分。

R1-Zero 的研究结果表明，随着强化学习训练推进，模型逐渐表现出：

* Reflection：回顾和修正已有推理。
* Verification：检查中间结果或最终答案。
* Alternative Strategies：尝试不同解题策略。
* Long CoT：生成更长的推理过程。

论文还展示了模型在训练中越来越多使用类似 `wait` 的表达，作为推理模式发生变化的可观察现象。[1]

但这些行为为什么会出现？

### 5.1 先理解一个简单的因果关系

假设一个模型面对复杂数学问题，可以使用两种策略。

**策略 A：直接回答**

```text
理解问题
    ↓
快速推导
    ↓
输出答案
```

**策略 B：推导后进行检查**

```text
理解问题
    ↓
尝试解法
    ↓
得到初步结果
    ↓
检查推导
    ↓
发现可能存在的问题
    ↓
修正错误
    ↓
输出答案
```

假设对于某一类问题，策略 B 更有可能得到正确结果。

如果训练目标奖励最终正确性，那么从长期统计上看，采用策略 B 的回答轨迹可能更容易获得较高 Reward。

强化学习并不需要提前知道：

“检查答案是一种好的认知策略。”

它只需要通过大量训练发现：

**某些生成行为与更高的期望奖励相关。**

于是，包含检查、修正或者重新尝试的输出策略，就有机会在训练过程中被强化。

这可以解释，为什么即使没有人为规定具体的 reasoning trajectory，模型也可能逐渐表现出复杂的推理模式。

不过这里需要保持严谨：

**论文观察到这些行为随着 RL 训练出现和增强，并不意味着每一句看似反思的文字都真正提高了正确率，也不能把这些文字直接等同于人类的内在思考过程。**

我们观察的是模型的输出行为及其与任务表现之间的关系。

### 5.2 Reflection：为什么模型会重新审视自己的答案？

Reflection 可以理解为：

**模型在生成过程中，对之前的推导或结论进行重新审视，并可能调整后续解题策略。**

例如：

```text
我通过方法 A 得到了结果 X。

等等，这个结果似乎不满足原始条件。

重新检查之前的假设……

发现第二步存在错误。

尝试方法 B。

得到新的结果 Y。
```

如果这种行为能够减少错误、提高获得正确答案的概率，那么它就可能受到强化学习的正向选择。

关键在于：

**Reward 不需要直接奖励“反思”这个词，而可以通过最终结果间接影响相关行为。**

### 5.3 Verification：为什么模型会主动检查？

Verification 指的是验证已得到的结果。

例如，求出：

$$
x=4
$$

模型可以进一步进行代入检查：

$$
2\times4+6=14
$$

确认结果满足原方程。

对于复杂推理任务，验证可能更加重要，因为中间环节中的一个错误就可能导致最终答案错误。

因此，在能够提高成功率的情形下，生成额外的验证步骤是合理的策略。

不过，模型**生成了一段验证文本**，并不保证它真的完成了可靠验证。

如果验证过程本身有错误，或者只是在重复之前的结论，那么长篇检查依然可能没有效果。

### 5.4 Long CoT：为什么推理过程越来越长？

CoT 是 Chain of Thought，通常指模型生成的分步骤推理文本。

Long CoT 则代表模型可以使用较长的输出序列完成多阶段推理。

对于复杂问题，较长的推理过程可能提供更多机会来：

```text
Problem
   │
   ▼
分析问题
   │
   ▼
尝试方法 A
   │
   ▼
检查中间结果
   │
   ▼
尝试方法 B
   │
   ▼
修正错误
   │
   ▼
验证最终答案
   │
   ▼
Final Answer
```

这可以理解为模型在推理时使用了更多 **Test-time Compute（测试时计算）**。

而 R1-Zero 的研究观察到，在强化学习训练推进的过程中，模型生成的推理长度也呈现增长趋势。[1]

这种现象说明：

**当更长的推理轨迹有助于解决问题，并且训练允许模型探索这类轨迹时，强化学习可能提高它们出现的概率。**

但是，一定不能把这个结论理解为：

> 推理文本越长，模型就越聪明。

因为 Long CoT 也可能带来：

* 无意义的重复。
* 不断绕圈却无法得出答案。
* 对错误结论进行过度解释。
* 更高的 Token 消耗与推理延迟。

所以更准确的理解是：

> **Long CoT 是模型可能学到的一种增加推理计算的策略，而不是最终训练目标，更不是推理正确性的保证。**

### 5.5 我对这一现象的理解

这其实揭示了一个重要的机器学习思想：

**训练目标不一定需要直接规定全部行为细节。**

我们设计优化目标，模型通过训练探索实现该目标的策略。

例如：

```text
直接优化目标：
提高最终答案正确率
          │
          ▼
模型探索输出策略
          │
          ├── 分解问题
          ├── 尝试不同方法
          ├── 检查中间结果
          └── 修正错误
          │
          ▼
某些策略提高成功率
          │
          ▼
相关行为在训练中被强化
```

这也是为什么 R1-Zero 的研究具有重要意义。

它展示了：**在合适的任务、模型能力和奖励机制下，复杂的推理行为可以不依赖人工逐步示范，而通过强化学习得到发展。**

## 六、R1-Zero 和 R1 到底有什么区别？

理解了 R1-Zero，我们再来看正式的 DeepSeek-R1。

### 6.1 R1-Zero：验证研究假设

R1-Zero 主要回答一个研究问题：

**不先进行 reasoning SFT，直接在 Base Model 上进行大规模 RL，能否显著增强推理能力？**

研究结果表明，这条路线是有效的。

但 R1-Zero 存在一些明显的问题，包括：

* 生成内容的可读性较差。
* 可能出现中英文混杂。
* 容易出现重复等不理想行为。
* 作为通用助手的体验仍有不足。

因此，R1-Zero 更适合被理解为一次重要的训练范式实验，而不是最终的完整助手训练方案。

### 6.2 R1：在推理能力基础上提高可用性

正式的 DeepSeek-R1 引入了更加完整的多阶段训练流程。

```text
              DeepSeek-V3-Base
                       │
                       ▼
                 Cold-start SFT
                       │
                       ▼
                 Reasoning RL
                       │
                       ▼
              Rejection Sampling
                       │
                       ▼
                Additional SFT
          (Reasoning + General Data)
                       │
                       ▼
                  Second RL
       (Reasoning + Human Preferences)
                       │
                       ▼
                  DeepSeek-R1
```

根据正式论文，其核心过程如下。[1]

**第一阶段：Cold-start SFT**

先利用相对少量的高质量推理示范，为模型提供更清晰、更符合人类阅读习惯的推理输出形式。

Cold-start 的作用不是取代后续的 RL，而是提供一个更合适的训练起点。

**第二阶段：Reasoning RL**

通过强化学习继续增强模型的推理能力。

这一阶段仍然重视可验证结果，同时还考虑输出语言的一致性等问题。

**第三阶段：Rejection Sampling + SFT**

通过对候选数据进行筛选，构建进一步监督微调所需的数据集。

这部分不只包含 reasoning 数据，也包含非 reasoning 的通用任务数据。

因此，模型不仅要能够解决数学或代码问题，还需要具备较好的通用助手能力。

**第四阶段：Second RL**

最后，再通过强化学习进一步优化模型的表现。

这里不仅包含 reasoning 相关奖励，还引入面向通用任务的人类偏好相关奖励，以改善 Helpfulness 和 Harmlessness 等属性。

### 6.3 两者的对比

| 维度                     | DeepSeek-R1-Zero | DeepSeek-R1      |
| ---------------------- | ---------------- | ---------------- |
| 训练起点                   | DeepSeek-V3-Base | DeepSeek-V3-Base |
| RL 前是否进行 reasoning SFT | 否                | 是，使用 Cold-start  |
| 核心目的                   | 探索纯 RL 激励推理行为    | 构建更完整、实用的推理模型    |
| 奖励信号                   | 主要使用规则奖励         | 结合规则奖励与模型化偏好奖励   |
| 训练流程                   | 直接进行大规模 RL       | 多阶段 SFT + RL     |
| 主要问题或目标                | 推理行为的形成机制        | 推理能力、可读性与通用能力的平衡 |

因此，我们可以把两者总结为：

> **R1-Zero 重点证明：推理能力可以通过不预先进行 reasoning SFT 的强化学习得到显著提升。**
>
> **R1 重点解决：如何在保留强推理能力的同时，通过多阶段训练改善可读性、通用能力及人类偏好对齐。**

还有一个值得注意的事实：

**最终的 DeepSeek-R1 并不是完全依赖规则奖励的纯 RL 模型。**

它将基于可验证结果的奖励与面向通用任务的人类偏好奖励结合起来。

这也是下一节理解 RLVR 和 RLHF 关系的关键。

## 七、RLVR 和传统 RLHF 最大的区别是什么？

这是本文最重要的问题，也是理解 DeepSeek-R1 训练路线的核心。

### 7.1 RLHF 是什么？

RLHF 全称：

**Reinforcement Learning from Human Feedback**

即基于人类反馈的强化学习。

传统 RLHF 的一个典型实现是：

```text
               User Prompt
                    │
                    ▼
             LLM 生成候选回答
                    │
                    ▼
               人类偏好标注
                    │
                    ▼
             Preference Dataset
                    │
                    ▼
               Reward Model
                    │
                    ▼
                RL Training
```

例如，用户问：

```text
帮我写一封礼貌拒绝工作 Offer 的邮件。
```

模型生成两份回答。

回答 A：语气生硬，但能表达拒绝。

回答 B：语气自然、礼貌，清楚表达了感谢和拒绝。

人类标注者可能更加偏好 B。

通过收集大量类似的偏好比较，可以训练一个 Reward Model，使其学习预测哪些回答更符合人类偏好。

然后，强化学习利用这些奖励信号优化模型。

经典的 InstructGPT 研究就采用了人类示范、回答排序以及基于奖励模型的强化学习这一训练路线。[5]

RLHF 很适合处理这类问题：

**什么样的回答更符合人类的需求、偏好和价值判断？**

### 7.2 RLVR 是什么？

RLVR 全称：

**Reinforcement Learning with Verifiable Rewards**

即基于可验证奖励的强化学习。

它的核心流程可以表示为：

```text
              Reasoning Problem
                     │
                     ▼
                LLM 生成回答
                     │
                     ▼
                  Verifier
                     │
               ┌─────┴─────┐
               │           │
             Correct     Incorrect
               │           │
               └─────┬─────┘
                     │
                     ▼
                   Reward
                     │
                     ▼
                RL Training
```

例如：

```text
数学任务：
最终答案是否符合标准答案？

代码任务：
生成的程序是否通过测试？

形式化证明：
结果是否通过 Proof Checker？
```

这里不需要依靠一个学到的偏好模型，去推测人类是否喜欢这份回答。

对于可可靠验证的结果，可以直接使用 Verifier 产生奖励。

### 7.3 最核心的区别：Reward 从哪里来？

| 对比维度    | 传统 RLHF                                    | RLVR                                           |
| ------- | ------------------------------------------ | ---------------------------------------------- |
| 全称      | Reinforcement Learning from Human Feedback | Reinforcement Learning with Verifiable Rewards |
| 核心奖励来源  | 人类反馈或由偏好数据训练的 Reward Model                 | 可自动验证的规则或环境反馈                                  |
| 主要关注    | 是否符合人类偏好和需求                                | 是否满足可验证的正确性条件                                  |
| 典型应用    | 对话、写作、通用助手对齐                               | 数学、算法编程、形式化任务                                  |
| 反馈成本    | 需要收集人类反馈，Reward Model 可自动评分                | Verifier 便宜可靠时可大规模自动评分                         |
| 主要风险    | 偏好偏差、Reward Model 偏差                       | 验证覆盖不足、规则漏洞、Reward Hacking                     |
| 是否使用 RL | 是                                          | 是                                              |

所以：

**RLVR 和 RLHF 的最大区别，不是有没有使用强化学习，而是 Reward 的来源和可靠性依据不同。**

传统 RLHF 主要依据人类偏好信号。

RLVR 则主要依据可验证的结果信号。

两者也不是互斥的。

在实际训练中，可以对数学和代码任务使用规则奖励，对开放式问答和通用助手任务使用偏好奖励。

DeepSeek-R1 的多阶段训练就是这种互补关系的一个具体例子。[1]

### 7.4 为什么 RLVR 对 Reasoning 特别重要？

假设我们想让模型学会解决复杂数学题。

使用人工推理示范的方式：

```text
大量题目
   ↓
专家编写完整解题过程
   ↓
构造 SFT 数据集
   ↓
模型学习模仿这些过程
```

而采用 RLVR 思路：

```text
大量题目 + 标准答案
             ↓
       模型自主生成解法
             ↓
       Verifier 检查结果
             ↓
        生成 Reward
             ↓
          RL 更新
```

这里发生了一个重要变化：

**训练不再必须依赖人工提供每一道题完整的推理轨迹，而可以通过验证结果来提供学习信号。**

这让模型获得了探索不同推理策略的空间。

例如，对于同一道题，模型可以尝试代数方法、枚举方法或其他求解策略。

训练系统不需要预先规定哪一种方法一定最好。

只要某种策略在统计上更有利于得到正确答案，它就可能在 RL 中得到强化。

不过，需要注意两个概念并不完全等价：

* **Outcome Supervision**：依据结果进行监督。
* **Process Supervision**：依据中间步骤进行监督。

R1-Zero 的关键实验重点在于利用结果正确性激励推理，而不是依赖人工逐步推理标注。

但 RLVR 并不意味着只能使用最终答案奖励。如果中间步骤可以被可靠验证，同样可以设计可验证的过程奖励。

因此：

> **RLVR 的核心是 Reward 可验证，而不是强制要求 Reward 只能来自最终答案。**

## 八、RLVR 并不是万能的：还存在哪些问题？

理解一种技术，不仅要知道它为什么有效，也要知道它在什么条件下可能失效。

### 8.1 Verifier 不可靠怎么办？

RLVR 的效果很大程度上依赖 Reward 的可靠性。

例如，某段代码通过了所有已有测试。

但是测试遗漏了一个重要边界条件。

于是：

```text
实际上存在 Bug 的代码
            ↓
      通过已有测试
            ↓
       得到高 Reward
```

训练系统可能错误地强化了这类回答。

因此：

**可验证并不意味着绝对正确，Verifier 的质量决定了 Reward 的可信程度。**

数学答案解析错误、测试用例不足、环境配置问题，都可能导致奖励信号失真。

### 8.2 Reward Hacking

Reward Hacking 指的是：

**模型找到了提高 Reward 的方法，但这种方法并没有真正实现我们希望的任务目标。**

例如，一个自动评分系统只检查某些固定测试。

模型可能找到一种能够通过这些测试，却不能正确处理一般输入的实现方式。

此时模型优化了评分指标，但没有真正提高我们关心的完整任务能力。

DeepSeek-R1 的 Nature 论文也指出，对于写作等难以构造可靠奖励的任务，如果使用神经网络 Reward Model 进行大规模强化学习，可能面临 Reward Hacking 问题。[1]

这提醒我们：

**奖励函数只是现实目标的一种近似，不一定能够完整表达真实目标。**

### 8.3 更长的 CoT 不代表一定更好

如果只关心正确性，而没有充分考虑计算成本，模型可能逐渐产生很长的输出。

但并不是所有额外的 Token 都有效。

因此，在实际系统中，我们可能还需要考虑：

* 最终答案正确率。
* 推理 Token 消耗。
* 推理延迟。
* 对不同难度任务的适应能力。
* 输出行为的稳定性。

这意味着未来的推理模型优化，不应该只关注让模型“想得更久”。

更重要的是：

**让模型在合适的时候，用合适的计算成本，完成有效的推理。**

## 九、从 DeepSeek-R1 中真正学到了什么？

回顾这篇论文，我认为最值得带走的不是某个具体算法公式，而是三个更底层的认识。

### 9.1 推理能力不只能通过模仿推理示范获得

SFT 能够让模型学习高质量的解题轨迹。

但 R1-Zero 展示了另一条有效路线：

**对于具有可靠 Verifier 的任务，可以通过强化学习直接优化解题结果，并在过程中发展出复杂的推理行为。**

这意味着人工提供完整推理示范，并不是增强模型推理能力的唯一途径。

### 9.2 Reward Design 是训练系统的重要部分

表面上看，我们在训练一个 LLM。

但实际上，模型最终会学习什么行为，很大程度上取决于我们如何设计训练目标。

```text
Reward Design
      │
      ▼
决定哪些结果被鼓励
      │
      ▼
影响模型探索的策略
      │
      ▼
影响训练后的行为分布
```

如果奖励机制可靠，模型更可能学习到有价值的策略。

如果奖励机制存在明显漏洞，模型也可能学习到利用这些漏洞的行为。

因此，设计训练系统时，不应该只关注模型结构和训练算法。

**Reward Function 和 Verifier 同样是核心组件。**

### 9.3 下一步的重要问题，是如何构造更多可靠的验证环境

数学和算法编程能使用 RLVR，一个重要原因是它们在很多场景下存在相对明确的正确性判据。

但现实世界中有大量任务并不容易验证：

```text
这个商业决策是不是合理？

这个软件架构是否便于长期维护？

这个 Agent 是否真正完成了用户目标？

这个回答是否有效解决了用户问题？
```

如果我们能够为更多复杂任务设计可靠的环境反馈和验证机制，就可能把 RLVR 的应用范围扩展到更广泛的领域。

对于 Agent 尤其如此。

一个 Agent 不一定需要通过人类偏好来判断每一步行动好不好。

在合适的环境下，也可以根据任务是否完成、工具是否执行成功、系统状态是否达到目标等信息，构造可验证反馈。

但这些信号是否真正代表任务成功，仍然需要谨慎设计。

因此，我认为 DeepSeek-R1 带来的一个重要启发是：

> **除了研究如何让模型生成更好的答案，我们还需要研究如何可靠地判断一个答案或行动到底好不好。**

## 十、面试时如何解释 DeepSeek-R1？

如果面试官问：

**“你认为 DeepSeek-R1 最重要的贡献是什么？”**

我的回答会是：

> DeepSeek-R1 最值得关注的地方，是它展示了强化学习对大模型推理能力的激励作用。
>
> R1-Zero 从预训练好的 DeepSeek-V3-Base 出发，不先使用人工标注的 reasoning SFT 数据，而是通过 GRPO 和规则型奖励直接进行大规模强化学习。
>
> 在这个过程中，模型逐渐表现出更长的 CoT、Reflection、Verification 和尝试不同解法等行为。这说明在数学、代码等具有可靠 Verifier 的任务上，不必完全依赖人工规定推理过程，也可以通过结果奖励来增强推理能力。
>
> 不过 R1-Zero 仍然存在可读性差、语言混杂等问题，因此最终的 DeepSeek-R1 引入了 Cold-start SFT、Rejection Sampling 和多阶段 RL，使推理能力与通用助手能力得到更好的结合。
>
> 而 RLVR 与传统 RLHF 的核心区别，在于前者主要利用可验证结果产生奖励，后者主要利用人类偏好或偏好模型产生奖励。二者并不互斥，可以在同一个训练系统中结合使用。

如果还能继续展开，我会补充一个观点：

**R1 的重要性不仅在于模型会生成 Reflection，而在于研究人员展示了：我们可以通过设计可靠的结果奖励，让模型在训练过程中探索能够提高问题解决成功率的行为。**

## 十一、总结与思考

最后，用一张知识关系图总结本文。

```text
                     DeepSeek-R1
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
         R1-Zero                       R1
             │                         │
      Base Model + RL          Cold-start + Multi-stage
             │                         │
             ▼                         ▼
       Rule-based Reward       Rule + Preference Reward
             │                         │
             ▼                         ▼
          GRPO                    SFT + RL
             │                         │
             ▼                         ▼
     Reasoning Behaviors       Reasoning + Usability
             │
      ┌──────┼───────────┐
      │      │           │
      ▼      ▼           ▼
  Reflection Verification Long CoT
```

理解 DeepSeek-R1，我认为需要记住以下四点：

**第一，R1-Zero 和 R1 并不相同。**

R1-Zero 重点研究纯 RL 能否激励推理行为；R1 则使用更完整的训练流程，在推理能力之外兼顾可读性、通用能力和人类偏好。

**第二，Reward 是强化学习的核心信号。**

模型并不是因为研究人员明确告诉它“你必须反思”，才表现出 Reflection，而是在优化奖励的过程中，某些有助于获得更高奖励的行为有机会得到强化。

**第三，数学和 Code 适合 RLVR，是因为它们在许多任务中具有可靠、自动化的验证方式。**

这并不意味着这些任务很容易解决，而是它们的结果相对容易判断。

**第四，RLVR 与传统 RLHF 最大的区别，在于奖励信号的来源。**

RLHF 主要依赖人类反馈或偏好模型，而 RLVR 利用可验证的任务结果。两者并不是竞争关系，而是可以互相补充的训练方法。

### 留给自己的三个问题

学完之后，可以尝试不看上面的内容回答：

1. 如果 R1-Zero 没有先进行 reasoning SFT，它为什么仍然具备一定的推理基础？
2. 如果我们只根据最终答案正确性提供奖励，为什么模型可能逐渐生成更长的推理过程？为什么这又不能证明 CoT 越长越好？
3. 假设你正在训练一个能够自动修复 GitHub Issue 的 Coding Agent，你会如何设计 Verifier 和 Reward？仅仅让单元测试通过，是否足以证明 Issue 已经被正确修复？

如果能回答这些问题，就不仅是在记住 DeepSeek-R1 这篇论文，而是在开始理解如何设计一个基于强化学习的 Reasoning System。

**最后留下一个值得继续研究的问题：**

> 当模型已经具备一定的基础能力，而强化学习又能够利用可靠奖励不断提高任务表现时，下一代推理系统的重要瓶颈，会不会不只是模型本身，还包括我们能够为多少复杂任务构造出真正可靠的 Verifier？

这个问题也可以自然延伸到后续的 Process Reward Model、Reward Hacking、Test-time Scaling 和 Agent Reinforcement Learning。
